# 企微新增客户管理第一期方案

> 实施更新（2026-09-10）：已在 `customer-management/phase1` 实现可本地运行的第一期应用，并验证演示流程；运行方式、实际复用范围及待完成的真实企微联调见 [交付说明](../customer-management/phase1/README.md)。以下保留原选型方案。

第一期只解决客户添加企业微信后的管理：客户自动进入名单、明确负责人、记录需求、安排跟进、更新进展。暂不关联小程序账号、生成方案、报告及订单。

在这个范围下，优先验证现成的开源企微 SCRM，比围绕小程序继续扩展自研更合适。原因是需求已收敛到标准客户管理，开源系统中可复用的部分变多，而小程序业务整合工作暂时不需要。选择必须以实际公开版本能够完成核心流程为条件。

## 一 最简单的业务流程

客户添加企微员工 → 自动进入客户列表并关联该员工 → 员工确认需求和分类 → 填写跟进记录及下次联系时间 → 更新状态 → 到期提醒继续跟进。

客户还没有小程序账号、没有手机号或没有填写需求，也应该先进入名单，后续由员工补充。不要求客户为了进入管理系统再登录、注册或填写一套表单。

默认由客户实际添加的员工负责，第一期可以人工调整业务负责人。同一客户添加多个员工时，应保留员工关系，不把姓名或手机号相似的客户直接合并。业务负责人调整和企微好友关系转接是两项不同操作，不能把改负责人显示为好友已经转接成功。

## 二 第一期开哪些功能

| 功能 | 实际使用方式 | 最低验收要求 |
|---|---|---|
| 客户自动同步 | 新增客户自动出现在列表，原有客户可以初始化导入 | 真正加好友才算新增，重复事件不重复建档 |
| 负责人 | 默认显示实际接待员工，主管可分配业务负责人 | 每个待跟进客户有人负责或明确待分配 |
| 分类和标签 | 记录咨询类型、意向程度和简单需求 | 员工能快速筛出需要处理的客户 |
| 跟进记录 | 每次填写联系结果、备注、下次联系时间 | 同事接手时能了解上次谈到哪里 |
| 提醒和状态 | 提供今日待办、逾期未跟进及状态筛选 | 到期能看到或收到提醒；成功完成后关闭待办 |

客户状态建议只保留：新客户、跟进中、已成交、暂缓、无效。这里的已成交先作为人工管理状态，不自动代表已收款。后续若需要经营收入统计，再引入订单或收款核验。

标签从少量固定选项开始，例如“建房咨询、设计咨询、造价咨询、合作咨询”和“高、中、低意向”。不先建设复杂评分模型。微信昵称、企微标识、员工关系和添加时间尽量自动取得；需求摘要、联系方式和跟进结论由员工按实际情况补充。

后台先保留三个主要页面：客户列表、客户详情、我的待办。主管增加按员工查看的新增、待处理、逾期和人工标记成交数量。第一期不做复杂渠道归因、销售预测、自动营销和聊天内容分析。

## 三 自研与开源怎么选

| 方案 | 当前优势 | 当前成本或不足 | 判断 |
|---|---|---|---|
| 在现有后台自研 | 已有线索、跟进记录、负责人和待办筛选页面；团队可沿用 Go 与 React | 仍需补通用企微客户同步、真实员工关联及关系变更处理 | 是可靠备选，尤其当团队熟悉现有系统且不愿维护第二套系统 |
| 采用开源企微 SCRM | 客户、员工、标签及加客能力更贴近现阶段需求 | 需要部署、企微配置及公开版验收；结构化跟进和提醒不能只凭演示认定存在 | 优先验证，核心功能通过后使用 |
| 采用通用 CRM | 一般具有线索、机会、任务等标准销售功能 | 还要接入企微客户联系，增加适配工作 | 第一阶段不优先 |

因此，建议先走“开源企微 SCRM 验证通过后独立使用”的路线。不需要建立与小程序的身份映射或订单同步。若候选系统连基本跟进记录、提醒都需要大改，或者部署维护成本高于扩展现有后台，就回到现有工作台增量开发，不为采用开源而增加复杂度。

如果实际只需要联系人名单、备注和标签，也可先用企微原生功能。是否需要独立系统，主要看是否要求统一跟进记录、到期提醒、跨员工查看及主管统计；这些才是本次第一期方案的选型标准。

## 四 开源候选只先验证一个

源雀 Iyque-SCRM 可作为首个验证候选。其公开仓库列出客户和员工列表同步、客户标签、员工活码、欢迎语等能力，采用 Spring Boot 和 Vue 3，LICENSE 标示 Apache 2.0。[项目说明](https://github.com/IYque/Iyque-SCRM)；[许可证](https://github.com/IYque/Iyque-SCRM/blob/master/LICENSE)。

这些资料足以将它列入候选，但尚不足以认定“结构化跟进记录、下次跟进时间、提醒、员工数据权限”全部满足本方案。必须用实际公开版本逐项验证，并核对商业版差异和项目要求保留的品牌信息。现阶段没有部署实测，也没有把选型建议写成已完成上线。

LinkWeChat 可作次选，但同名代码来源和分支较多，需要固定仓库、版本与许可后再比较。[所查公开仓库](https://github.com/Link-WeChat/link-wechat)。

悟空当前 Wukong AICRM 的许可证明确将企业经营和生产使用纳入需商业授权的范围，不按免费开源生产方案考虑；这一结论不泛指所有历史悟空版本。[当前许可证](https://github.com/WuKongOpenSource/Wukong-AICRM/blob/main/LICENSE)。

## 五 实施和验收保持简单

先在隔离环境部署选定公开版本，连接少量测试员工，用测试客户完成“加好友、同步、记录、提醒、改状态”的完整过程，再导入现有客户并让少量员工试用。通过后扩大使用，迁移时保留原始企微标识及员工对应关系。

只验收以下六件事：

1. 新客户添加员工后能自动进入名单；重复同步不会产生重复客户。
2. 员工只能访问授权范围内客户，主管能按管理范围查看。
3. 每次跟进能保存结果和下次联系时间，提醒真正可用。
4. 客户删除、重新添加或多员工跟进时，名单与关系记录合理。
5. 能导出客户与跟进记录，并完成一次备份恢复验证。
6. 同步失败可以发现并补同步，不会悄悄漏掉客户。

这些基础正确性仍需要保留，但不要求第一期开发一套复杂架构。欢迎语可先用现成配置；聊天主要继续在企微进行，跟进结果由员工手工记录。未开通并验证会话存档等能力前，不假定系统能自动读取员工与客户的全部聊天。

上线前需要落实企微管理员、允许接入的员工范围、测试账号、部署环境及维护责任人。当前没有这些实际配置和运行验证，不给出确定上线日期或成本承诺。

该方案依据 2026-09-10 可读取的工作区源码和公开项目资料制定；不以小程序深度绑定作为第一期前提。企微开发者站点此次访问受限，具体接入权限和接口条件需在实际配置阶段核验。
