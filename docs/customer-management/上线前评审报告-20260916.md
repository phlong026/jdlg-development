## 2 总体结论

**有整改条件通过。** 代码质量、权限设计和文档治理明显高于常规内部项目水平；但存在 4 个上线阻断项（P0）与环境验收缺口，完成整改并按第 6 节清单执行后可安排发布。不建议当前状态直接上线。

要点：

1. 架构选型正确：复用而非重写，Go 统一入口 + HMAC 桥接 + Java 主档，职责边界在代码与文档中均成立，前后端接口无断链。
2. 完成度高：S01—S06、T01—T10 全部本地交付，09-15 验收的 12 项代码评审修复均有对应实现；冲突分析中的 C02（Java 慢响应拖住全后台）、C03（CORS 预检缺 X-CRM-Request）已在最近提交中修复（`ManagementSession.tsx:17-19`、`route/cors.go:36`）。
3. 本轮新发现 1 个全后台级安全漏洞（CORS 反射任意 Origin，P0-1）和 2 个需要负责人拍板的风险项（P0-3、P0-4），详见第 5 节。
4. 真实企微接入、真机验收、生产部署演练仍未开始，这是文档如实记录的边界，不是缺陷；但意味着"开发完成"不等于"可上线"。

## 3 架构分析

### 3.1 结构

```
浏览器（React 后台 /admin/customer-management，同源相对路径）
   │  session cookie（账密 / 企微 OAuth 双通道）+ 写操作 X-CRM-Request + Origin 校验
   ▼
Go 网关（service/）── 登录、限流、management_access 授权（platform_admin / crm_only）
   │  HMAC-SHA256 内部签名（kid/ts/nonce/method/path/body 摘要，防重放）
   ▼
Java 客户服务（customer-management/phase1）── 客户主档、归属、跟进、附件、公海、企微同步（/internal/management/v1，不暴露公网）
   ▲
   └─ 小程序线索 outbox 同步（customer_lead_crm_delivery 检查点，失败重试）
```

### 3.2 数据职责（现状与设计一致）

| 数据 | 写入方 | 说明 |
| --- | --- | --- |
| 客户主档、跟进、附件、公海 | Java | 唯一业务写入点；Flyway V1—V5 增量迁移 |
| 平台授权、账号关联、企微身份绑定 | Go | `management_access` / `management_crm_link` / `management_wecom_identity`，乐观锁 + 审计 |
| 小程序咨询线索 | Go | 旧入口保留只读，写接口 409 阻断（`customer_service.go:210-213`），防止绕过新规则 |
| 报告企微交付 | Go（reportwecom） | 与 CRM 共用企微事件，回调共存方案未落地（见 P0-2） |

### 3.3 架构优点

1. **权限三层叠加且前后端一致**：会话 → 平台 scope（crm_only 白名单限制在 `crm_bridge.go:41-50`，测试覆盖）→ 企微会话复核（绑定版本变更即踢下线）；前端菜单/页签/按钮限制与后端逐层对应，抽查未发现"仅前端隐藏"的越权面。
2. **服务间认证严谨**：HMAC 规范化签名含 nonce 防重放、body 摘要、不跟随重定向、20 秒超时、64KB 请求上限，两端共享测试向量。
3. **企微 OAuth 实现规范**：state 与浏览器双随机值仅存 SHA256、5 分钟一次性、强制 HTTPS 同源回调；token 进程内缓存、错误信息不泄密（有专项测试）。
4. **可靠同步设计**：小程序线索走 outbox + 检查点，成功应答才推进，重启可补投，UTF-16 边界截断防字段超长。
5. **诚实的过程文档**：完成/未完成边界、验证手段（模拟 SDK vs 真实企微）记录清晰，可审计、可交接。

### 3.4 架构风险与债务

1. **企微事件入口未统一**（P0-2，详见下节）：Go 报告回调与 Java CRM 回调都消费 `add_external_contact`，正式同时启用前必须落地分发方案。
2. **平台可用性与 Java 耦合**：授权保存的两阶段事务（本地禁用 → 远程开通 → 激活）在 Java 故障时阻塞平台权限调整（冲突分析 C05，未修复）；失败留 pending 行且无补偿任务，需人工重试。
3. **多实例部署不完整**：登录限流为进程内存（`management_login_gate.go`）、来源同步 worker 为进程内 TryLock（`crm_sources.go:117-124`）；单机宝塔部署可接受，扩多实例前需改集中式。
4. **前端双请求层并存**：`utils/request.ts`（Bearer 假 token + 401 硬跳）与 `api/wecomCustomers.ts`（cookie + 401 事件）策略不一致，长期维护隐患。

## 5 问题清单与修改意见

### P0 —— 上线阻断，发布前必须处理

**P0-1 生产 CORS 反射任意 Origin 且允许凭据（全后台漏洞，本轮新发现）**
`service/route/cors.go:17-35`：生产分支仅处理 Origin 为空的情况；Origin 非空时原样回显为 `Access-Control-Allow-Origin` 并附加 `Access-Control-Allow-Credentials: true`。注释写"只允许配置的来源"，代码实际未做任何白名单校验。任意第三方站点可在已登录管理员浏览器中跨源读取全部管理接口响应（订单、用户、配置），CRM 写操作虽有 Origin 白名单，其余管理接口无此保护。
修改意见：生产环境改为显式白名单（复用 `CRM_ALLOWED_ORIGINS` 或新增 `ADMIN_ALLOWED_ORIGINS`），未命中一律不下发 CORS 头；同源部署下合法请求不依赖 CORS，收窄零成本。补一条单元测试：陌生 Origin 响应不含 `Access-Control-Allow-Origin`。

**P0-2 报告企微回调与 CRM 事件回调共存方案未落地**
冲突分析 C01 已论证：报告链路（State/欢迎消息）与 Java CRM 建档依赖同一 `add_external_contact` 事件，直接把回调切给任一方都会断另一条链路；`reportwecom.Service.HandleEvent` 对陌生 State 会报错，不能简单并联。方案已给（Go 作统一入口、可靠存储后分发），但代码未实现。
修改意见：列为上线前第一个开发项，按冲突分析第 6 节验收标准执行（报告加好友同时完成交付与建档；普通渠道事件不触发报告错误重试）。若首期不上报告企微交付，需在发布记录中明确关闭 `REPORT_WECOM_ENABLED` 并把该决定写入操作手册。

**P0-3 存量管理员授权迁移是发布必做项，漏执行会锁死全部原后台**
`management_access` 表一旦建立，未登记的管理账号一律拒绝（`crm_bridge.go:53-87`），关闭桥接也不回退（`crm_bridge.go:65` 仅对无表+旧会话放行）。部署手册第 3 节已写明，但这是人为步骤，无代码保护。
修改意见：把"导出现有管理账号清单 → 逐个写入 `management_access(scope=platform_admin)` → 用每个账号实际登录验证"做成发布检查单签字项；发布窗口安排至少两名管理员交叉验证。同时验证 A01 关键原页面（总控台、订单、用户）不被误锁。

**P0-4 登录页明文密码写入 localStorage（需负责人知情拍板）**
`background/src/pages/login.tsx:77-84`：勾选"记住密码"后账号与密码原文存入 localStorage，任何 XSS 或本机访问即可窃取后台凭据；共用电脑风险更高。09-15 验收记录显示这是用户明确要求保留的行为，冲突分析 5.4 节也已建议"保留账号记忆、取消保存明文密码"。
修改意见（二选一，由负责人确认）：
- 方案 A（推荐）：改为只记住账号，密码栏自动聚焦；交互改动小，消除主要风险。
- 方案 B：保留现有行为，但在上线评审记录中书面确认接受该风险，并确认后台全站无已知 XSS 面（本轮未发现，但 CORS P0-1 修复前不满足此前提）。

### 8.3 遗留事项（有意保留，非遗漏）

1. **双请求层 401 策略统一**：`request.ts` 硬跳转与 `crm()` 事件驱动并存。两者均能正确登出，统一需改动全部非 CRM 页面的错误路径，建议随下一次大版本处理。
