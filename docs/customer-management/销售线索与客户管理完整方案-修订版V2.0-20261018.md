## 1. 目标与范围

### 1.1 业务目标

让每一项值得承接的需求都有明确负责人、下一步动作和可追溯结果；让来源、传播贡献、当前责任与成交事实各自准确。

统一业务主档和销售入口，保留独立的原始访问事实、身份、来源、跟进、附件、订单和历史。多张表、多个来源不等于业务重复；同一需求被重复分配、重复联系或重复计数才是需要解决的问题。

### 1.2 延续的产品边界

1. 不新增独立“商机”产品或一级菜单；按已确认 D12，在客户详情中管理多项独立“需求记录”。
2. 预算卡片保持现有效果，对方进入造价测算页；不能声称对方查看了分享人那份预算。
3. 本轮不建设完整合同、回款、财务、工程交付、渠道佣金结算或聊天存档系统。
4. 报告、会员、模板的订单、支付、退款、领取和交付结果仍以现有业务系统为准；CRM 展示引用，不制造另一份权威订单台账。
5. 页面以线索承接、客户跟进、待办、公海为日常入口；设置、同步与规则配置收在管理区。

## 3. 对象、关系与统计单位

### 3.1 业务结构（D01、D12 已确认）

建议在客户详情中区分以下对象，首层页面仍保持“客户、联系人、需求、动态”的业务语言，不要求员工理解库表。

| 对象 | 表示什么 | 必须保持的边界 |
| --- | --- | --- |
| 自然人及已验证身份 | 真实联系人、小程序账号、企业范围内的企微标识等 | 夫妻、父母、代理人是不同自然人，不能为了合并客户数而合并登录身份 |
| 客户业务档案 | 同一家庭或委托主体的建房业务关系 | 家庭关系必须人工核实，不凭相同地址、电话、转发自动认定 |
| 联系人关系 | 本人、配偶、父母、付款人、授权代理等与档案的关系 | 记录谁提供资料、谁能决策、谁应被联系；不自动共享个人权益 |
| 需求记录 | 一处地点、一个可独立推进和核算的需求 | 阶段、结果、金额、预计成交时间、当前责任与保护需有明确承载单位 |
| 来源记录 | 某次咨询、分享触达、企微关系或报备的来路 | 可以有多条；不能当成多个独立客户直接相加 |
| 动态与跟进 | 发生了什么、谁做了什么、下一步是什么 | 浏览和资料编辑不能伪装成真实人工联系 |
| 成交事实 | 某业务类型发生的签约/定金等被确认事件 | 与订单、收款、退款和履约分别引用 |

**已确认 D01-A（2026-10-18）：同一客户业务档案可由主管人工关联多个家庭联系人，标注关系、主要联系人和决策人；各人的小程序账号、企微身份和付费权益保持独立。** 不凭相同电话、地址或转发自动合并自然人身份；家庭关联不授予内部后台或他人付费内容访问权。D01 不决定是否支持多项需求。

**已确认 D12-A（2026-10-18）：在同一客户业务档案的详情中保存多项独立需求，每项分别记录地点、服务类型、阶段、金额、当前负责人、保护期和成交结果；旧需求不被覆盖。** 客户列表展示主要需求，首期提供必要的新增、切换和历史查看能力，不增加独立商机导航。

同一需求重复来访只追加来源/动态；同一人出现另一处宅基地或独立的新需求时，由有权人员核实后新建需求记录并关联原档案，不覆盖旧金额、阶段、成交凭证。

家庭共享需求不等于共享手机号、小程序账号、付费报告、会员权益或全部访问轨迹。家庭联系关系不能替代身份和订单授权。

D01 已选择家庭多联系人方案；首期须支持同一业务档案的家庭联系关系。同一自然人的多渠道身份仍按第 4 节核实关联，家庭多人不能混为同一自然人。

阶段、分配、认领、保护和成交转换均以档案内的独立需求为单位，不能因一项成交让其他需求永久免回收。原手动报备的编号、历史和合法保护不因后续模型迁移被清空；具体存储与迁移设计留待开发方案，不以本轮业务确认直接执行拆分或变更数据。

### 3.2 状态分维度管理

| 维度 | 业务含义 | 不得代替的事实 |
| --- | --- | --- |
| 客户资格 | 待核实 / 已确认 / 历史待核实 | 不能从 `lifecycle != pending` 推导全部都是合格客户 |
| 需求类型 | 建房销售 / 合作 / 待确认 | 不等于账号注册身份 |
| 线索处理 | 待分配 / 待联系 / 核实中 / 已转客户 / 无效 | 不承担“已成交”的含义 |
| 客户阶段 | 需求确认、现场资料、方案、报价、签约谈判、已成交 | 不等于负责人是否仍受保护 |
| 推进状态 | 进行中 / 暂缓 / 流失关闭 | 暂缓保留暂停前阶段；恢复不自动回到第一个阶段 |
| 联系意愿 | 可承接 / 已明确拒绝联系 / 待重新确认 | 再次浏览不能覆盖明确拒绝联系 |
| 归属状态 | 待分配 / 临时承接 / 保护中 / 公海 / 已结案 | 资料更新不自动续期或抢归属 |

这是业务语义，不要求立即为每个维度新建字段或表；技术设计必须证明所用字段组合可以表达上述区别。旧 `legacy`、`archived`、`pool` 要按真实业务资格解释，不直接混入客户或线索分母。

## 4. 多渠道识别、查重、家庭关联与纠错

### 4.1 关联证据分级

1. **已有明确映射**：在相同业务命名空间下，同一来源标识已绑定主档或联系人，复用该绑定；重复事件按事件标识幂等处理。
2. **新增可信绑定**：通过明确绑定流程确认的小程序身份与企微身份，记录验证方法、时间、操作者和适用范围。只有证据明确覆盖“同一自然人”时才自动关联身份。
3. **疑似重复**：同手机号、微信文本、姓名、地址、需求相似等，只生成核实任务。登录手机号也不能单独作为跨渠道自动合并依据；可能存在共用、代填和号码变更。
4. **同家庭或同需求**：由主管依据沟通确认家庭/委托关系及需求归属；关联业务关系，不把多个人的身份合为一人。
5. **无法识别**：保留来源和待核实原因，允许人工承接有真实联系渠道的企微/线下线索，不要求其先注册小程序。

疑似重复检查只返回“存在需核实记录”等必要信息；不得向其他顾问泄露受保护客户姓名、电话、地址、负责人详情。

### 4.2 合并与拆分

- 主管核实后选择保留主档，明确冲突资料、来源、联系人、需求、归属和保护如何保留；不能仅按最新修改时间自动选主档。
- 已有保护中的需求优先保留其有效归属。两边均有保护时，先裁定争议，不在合并中隐式转交。
- 保留原 ID/编号映射、原记录和操作依据；可追踪合并前后的字段、来源和历史。
- 误合并拆分时分别归还有证据的来源、联系人和需求；不确定内容进入主管核实，不向两边复制敏感资料。
- 拆分不自动新开 90 天保护，不把成交恢复成线索。恢复哪份原归属、期限及阶段须在纠错记录中明确；原期限已过期则按当前权限进入公海或核实状态。
- 合并、拆分、家庭关联、客户资格转换分别记事件，不能相互替代。
- 解除家庭/委托关系不合并或拆开登录身份，不复制已关联档案的敏感资料。重算关系和当前访问范围，撤销由该关系产生的访问引用，需求及保护只保留有证据的原承载；不能以解除家庭关联新开保护或清空真实成交。

### 4.3 匿名与登录

匿名访问只进入内容效果和候选观察。可信会话关联成功后，可把证据覆盖范围内的历史挂到已识别联系人；不扩大为“全部历史已识别”。跨设备、跨浏览器、过期或证据不足的访问保留未关联状态。

关闭分析后缺少行为数据不妨碍主动留资、电话、企微或手动报备。评分缺失显示“证据不足”，不能显示为低意向或无需求。

## 5. 进入线索的条件与需求分流

### 5.1 各入口的规则

| 入口 | 推荐处理 | 去重与后续动作 |
| --- | --- | --- |
| 主动留电话、明确请求人工联系 | 有可用联系渠道则进入线索，优先承接 | 同需求已有记录则追加咨询及待办，不重新分配或续期 |
| 真实企微新增好友 | 先存真实关系，形成待核实线索 | 同企微身份不重复建档；加第二位员工保留关系，不覆盖业务负责人 |
| 已登录访客达到行为阈值 | 进入候选池；人工确认后承接，是否自动化见 D06 | 候选不是独立客户，不直接进入销售分母 |
| 匿名高活跃 | 只观察，提供现有客服/留资入口 | 不产生需要顾问“联系”的虚假待办 |
| 顾问手动报备 | 视为已经当面或实际联系后的显式确认 | 查重、资料与责任确认一并记录；满足 D02 后进入客户保护 |
| 需求草稿、点击生成、普通 AI 问答、点击客服入口 | 保留动态或草稿 | 不冒充主动请求、真实加企微、报价或成交 |
| 已有客户再次进入 | 追加来源、需求变化和必要待办 | 家庭关系按 D01、新需求承载按 D12 核实，不自动开新客户 |

### 5.2 可联系与优先级

可联系渠道包括客户明确提交的电话/微信、已验证有效企微关系、已有可使用的沟通关系。账号绑定电话与本次明确留作联系的电话分别保存来源，不因补号覆盖客户指定联系人。

确需从已有账号资料补联系方式时，需遵守已有产品告知、字段权限和客户联系意愿，标记“账号绑定号码，待核实”；号码存在、格式正确、已经联系成功是三种不同事实。

无可用渠道的行为候选保留为待补联系信息，不记作已可承接线索，不进入联系超时和首次响应分母。客户已主动提出联系但资料无效时进入“联系信息异常”处理，由主管查缺，而不是持续派给顾问拨打。

主动咨询高优先与行为评分高低分别展示。转人工 +40 分不意味着必须被标成 ≥60 分的行为高意向；“主动请求”足以排在优先承接队列。

### 5.3 销售与合作（待确认 D03）

推荐按本次需求分流，注册身份作为初始提示：设计师为自家建房可进入销售；业主咨询加盟可进入合作。同一联系人可以有关联的销售需求和合作需求，分别处理和统计。

身份为空保留“身份待确认”，不直接判低质量。信息矛盾或混合需求由主管核实；不能只凭账号改身份自动转换人工已确认的 CRM 类型。

如选择沿用严格身份分流，则正文与验收同步改为“B 端进入合作，个人建房个案由主管例外确认”；不能一边硬拦截，一边承诺完全覆盖 B 端个人建房。

合作线索由主管统一处理，不进入销售认领、销售保护和销售转化分母。保留待处理、处理中、达成合作、结束及原因；本轮不延伸建设合作佣金或完整合作 CRM。

## 6. 来源、分享贡献与当前归属

### 6.1 分别记录的事实

| 信息 | 作用 | 发生转交、回收、认领时 |
| --- | --- | --- |
| 首次获客来源 | 解释最初如何进入 | 保留原事件及当时规则 |
| 本次入口/最近触点 | 解释本次咨询和行动上下文 | 追加记录，不覆盖首次来源 |
| 直接分享人/转介绍人 | 解释谁参与传播 | 保留自然人/员工身份及证据快照 |
| 上游传播链 | 查看已知传播路径 | 证据不足、过期或删除时标明链路不完整 |
| 当前负责人 | 明确现在由谁承接 | 仅授权分配、主管交接、回收认领等动作可改变 |
| 历史负责人及贡献 | 追溯历史工作 | 不随离职或现负责人变化被清空 |

归属规则只解决业务承接；不据此自动产生佣金、奖励资格或金额。未来结算需另行确认业务规则与证据要求。

### 6.2 归属优先顺序

1. 先检查同人/同需求、明确拒绝联系、结案和合作分类，不能先按分享人建一条新的销售记录。
2. 同需求已有保护中的有效负责人：保持归属，只追加动态并按权限通知当前负责人。
3. 同需求已有正在承接、尚未到回收条件的线索负责人：保持承接，不被后来的访问或企微加人覆盖；保护尚未开始不等于人人可抢。
4. 同需求已经进入公海/待分配：按其认领/分配规则处理；不能用旧分享自动把需求重新分回原员工。
5. 真正全新需求：按可信来源推荐初始接待人；员工须有有效 CRM 授权和有效账号绑定，否则进入待分配并提示绑定异常。
6. 无法确定是否同需求、两个有效归属冲突：由主管核实；不向另一顾问泄露客户详情，不因争议自动延长保护。

### 6.3 新需求的首次分配

| 来源 | 推荐初始处理 | 决策状态 |
| --- | --- | --- |
| 直接分享人是有效员工 | 推荐该员工承接 | 沿用原方案方向；多个员工触达见 D05 |
| 直接分享人是外部人员 | 推荐待分配，记录外部转介绍人；上游员工仅记贡献 | 待确认 D04，消除“外部待分配”与“上溯员工归属”的冲突 |
| 公共入口主动留资 | 待分配，主管选择有效接待人 | 补强 |
| 真实企微新好友 | 添加员工为接待人；若已存在有效归属，保持原归属并保留新增关系 | 沿用 |
| 手动报备 | 经重复核实后由报备人承接 | 沿用 |
| 合作需求 | 主管队列 | 沿用合作需求独立处理方向 |

待确认 D05 推荐：只对尚未分配的全新需求，在可证明的 30 天窗口内取首次有效员工触达；后来的触达只记贡献。归属形成后不因滚动窗口过期重选。触达无证据、同一时间无法判定、跨权限事实不完整时进主管核实。

员工绑定及离职按事件发生当时的有效身份和当前可承接资格分别判断；后来绑定、解绑或改名不能重写历史传播身份。员工失效后交接处理，不把历史客户批量自动改给某个上游分享人。

## 7. 线索状态、实际联系与转客户

### 7.1 线索转换

| 事件 | 处理状态 | 业务约束 |
| --- | --- | --- |
| 新线索无人承接 | 待分配 | 显示原因与主管待办 |
| 分配给有效账号 | 待联系 | 记录本次 `assignedAt`，不开始客户 90 天保护 |
| 电话未接、消息未回复 | 仍待联系，增加联系尝试 | 不当成首次有效联系，不续期 |
| 电话接通/真实企微沟通/当面沟通，并有结论 | 核实中 | 记录操作者、时间、方式、需求结论和下次动作 |
| 满足 D02 的客户认定条件 | 已转客户 | 原子记录资格转换与负责人；仅在满足保护资格时起算 90 天，禁止同一转换重复计数 |
| 不符合需求或联系信息异常 | 按原因处理或申请无效 | 明确拒绝联系由主管归档，并设置联系限制 |
| 超时回收 | 待分配 | 保留已联系事实、历史负责人、沟通和需求，不伪装成全新线索 |

“已加微信”须区分“顾问已发送申请”和“已验证好友关系”；“已电话”须区分未接、接通和确认需求。快捷按钮必须保存真实结果，不能自动升级客户资格。

### 7.2 转客户（待确认 D02）

推荐条件同时满足：

1. 实际联系本人、家属或有权代理人，记录方式、顾问、沟通时间和结论；系统不声称自动验证通话/聊天内容。
2. 顾问明确确认真实建房/设计等本次需求，客户有继续沟通意愿。
3. 完成原五组报备资料：姓名与微信信息、联系电话、镇村地址、面积和需求、预计建房时间。微信沿用选填；预计时间允许真实的“待定”，不能为凑完整度伪造日期。
4. 当前负责人有效且明确，完成重复与归属检查。
5. 没有未解决的拒绝联系、归属争议或合并冲突。

转换保存独立的 `customerQualified` 事件及 `convertedAt`，与资料编辑、历史纳管、手动直接报备区分。手动报备提交中可完成同一人工确认，不能制造虚假的历史电话记录。

如果 D02 允许真实需求已确认但资料不齐先成为客户，则“客户资格”与“保护资格”分别记录：前者可先成立，五项资料与归属未满足前不开启 90 天保护。此替代会改变原转客户门槛，必须由用户明确选择。

### 7.3 线索时效（待确认 D07）

原稿的“4 工作小时、2/24 小时、48 小时、7/30 天”混合口径需统一。推荐：短期分配/首次响应按营业日历；长期沉默与 90 天保护按自然日。

| 队列 | 推荐时限 | 从何时计 | 到期动作 |
| --- | --- | --- | --- |
| 待分配 | 4 工作小时 | 线索达到可承接条件 | 提醒主管，不虚构负责人 |
| 高优先待联系 | 2 工作小时 | 分配成功且可联系 | 提醒当前负责人并升级主管可见 |
| 普通待联系 | 1 工作日 | 分配成功且可联系 | 提醒当前负责人 |
| 未有有效联系 | 2 工作日 | 本轮分配成功 | 满足已确认回收策略后回待分配；尝试联系不重置时钟 |
| 核实中无有效跟进 | 7 自然日提醒，30 自然日回待分配 | 最近有效联系；无则用本轮分配时间 | 保留历史，主管可查看回收原因 |
| 已排下次联系 | 到期即逾期 | 独立的下次联系时间 | 不等待 7 天提醒才显示 |

营业日历、节假日和时区需由主管在上线前配置，时区为 Asia/Shanghai；未配置不启用自动回收。上述时限均是本轮推荐，待 D07 确认，不能以文档生成时间当作生效时间。

回收前重新检查当前版本、有效跟进、联系承诺及当前归属。未来约定是否能暂停线索沉默回收，单独由 D14 决定；D07 选择时间口径不等于批准回收豁免。推荐只允许有客户明确约定证据、原因和截止时间的主管审批例外；选择不豁免时保留约定并转待分配/主管承接。两种都不能改变客户 90 天保护规则，也不能以普通备注豁免。

## 8. 客户阶段、保护、公海、暂缓与恢复

### 8.1 阶段与推进证据

下表是原稿人工设计/建房类需求的候选阶段模板，受 D09 最终业务范围约束，不能套用到所有产品。D09 确认后，针对实际经营的设计、造价、施工或转介服务分别保留适用阶段和证据；报告、会员、模板继续使用各自订单流程，不套销售六阶段。

| 阶段 | 主要工作与证据 | 建议停留提醒 | 备注 |
| --- | --- | --- | --- |
| 需求确认 | 地点、规模、需求、预算区间、预计时间、决策联系人 | 7 天 | 预算仍属参考 |
| 现场资料/勘察 | 照片、尺寸、报建或勘察记录 | 14 天 | 设计远程业务可用客户提供资料，不能伪称到场 |
| 方案沟通 | 方案附件、版本、客户反馈 | 21 天 | 生成工具结果不等于客户已确认方案 |
| 报价 | 正式报价依据、范围、金额和反馈 | 14 天 | AI 测算/预算不自动成为正式报价 |
| 签约谈判 | 服务范围、合同、付款节点和开工/交付约定 | 14 天 | 已付款报告不替代设计或施工签约 |
| 已成交 | 主管核实 D10 定义的业务凭证 | 不按停留催促 | 后续履约、收款、退款按各业务事实处理 |

阶段提醒天数是初始运营建议，可配置，不自动改变归属。允许跳阶段，需记录依据；不能跳过成交审批。阶段推进记录前后状态、时间、人员、证据，不因再次保存同阶段刷新阶段起点。

认领、交接、恢复核实不将原“方案/报价”自动重置为“新客户”；阶段需要纠正时由负责人明确操作并留痕。暂缓、流失作为推进状态，保留停下时的阶段与原因。

### 8.2 保护矩阵

| 动作/事实 | 是否续期或新开保护 | 其他影响 |
| --- | --- | --- |
| 首次完成有效报备 | 开始 90 天 | 记录首次起算及确认依据 |
| 保存有效联系结论；有效出图/报价有附件并完成记录 | 从服务端接受有效活动时重新计算 90 天 | 不能靠编辑历史时间回填占有 |
| 上传附件但未保存有效活动、改阶段、改资料、自动评分、再次咨询/加好友 | 否 | 只追加各自事实 |
| 主管交接 | 否，保留剩余期限 | 原账号立即失权，新账号承接待办 |
| 公海认领 | 新开 90 天 | 不增加获客数、不改变原阶段、不清空回访承诺 |
| 暂缓 | 否 | 继续计时，可因真实有效回访续期 |
| 提交成交申请 | 否 | 审批未完成仍按原规则计算 |
| 主管确认成交 | 退出该已成交需求的公海回收 | 不等于所有未来需求都永久归该员工 |
| 主管确认归档/明确拒绝联系 | 退出公开认领和自动营销待办 | 保留历史及恢复限制 |
| 无效跟进复核 | 按最近仍有效的活动重新算 | 保留原文、复核依据和责任人 |

按已确认 D12-A，阶段、归属、保护和成交由客户档案下的独立需求记录承载。同一有效需求仅一名当前负责人；同家庭原负责人优先协调，新需求需不同顾问时由主管分配，避免重复联系。成交需求关闭不自动豁免其他未成交需求，不以同家庭关联获得永久占有。

### 8.3 暂缓与回访（待确认 D08、D13）

暂缓保存原因、暂停前阶段；日期是否必填由 D13 决定。推荐必须有客户约定回访日或内部复核日，二者明确区分，内部复核不冒充客户约定联系；若允许无日期，则进入主管“暂缓待排期”队列。未来提醒与当前推进待办分别保存。客户明确要求回访日前不要联系时，系统不因新的浏览、评分或别人的分享提前产生普通销售外联待办。

推荐：保护到期进入公海时，原顾问失去访问，尚未完成的回访承诺转主管待办；认领后由新负责人继承。若回访日已到而无人认领，主管仍能看到，不能因入海自动删掉承诺。

### 8.4 无效、流失、拒绝联系和重新激活

| 原因 | 处理 | 后续重新访问 |
| --- | --- | --- |
| 重复记录 | 主管核实关联，来源不丢 | 归到正确记录，不产生新销售对象 |
| 空号/联系信息错误 | 标记渠道异常，允许补正 | 不靠分数自动解除异常 |
| 需求暂时无计划 | 有回访意愿则暂缓，否则结案待核实 | 浏览只作动态 |
| 选了别家/本次计划取消 | 本次需求流失关闭，记录原因 | 新主动咨询可进入主管恢复或新需求核实 |
| 明确拒绝联系 | 主管归档并限制主动销售触达 | 浏览、分享、规则升级均不自动恢复 |
| 身份/类型错分 | 主管纠正需求分类 | 不把纠错算新的获客或成交 |

恢复必须指明触发依据、恢复哪个需求、当前联系意愿和负责人；拒绝联系后的新主动请求，先记录用户本次明确诉求及允许联系范围，再由主管确认是否解除相应限制。恢复不擦除旧拒绝记录，不自动续期，不自动算新客。

## 9. 行为评分、候选与自动化

### 9.1 评分的含义

评分只表示近期行为值得关注的程度，不自动证明真实需求、购买能力、同一家庭或成交概率。顾问确认的需求质量、客户联系意愿、主动请求优先级与行为分数分别记录。

原稿分值可作为影子实验版本：会话 +5、可见停留每分钟 +2、核心内容 +8、重复查看 +10、转发 +10、收藏 +10、完成测算 +20，沿用每日上限；这些值尚未得到实际运营校准。30/60 分在影子期用于候选分层，推荐不直接作为自动开销售线索的充分条件（D06）。

### 9.2 证据规则

- 窗口、自然日、规则版本、计算时间、分项分数和排除原因可查；按北京时间自然日封顶。
- 会话、重复内容、转发请求与测算请求需分别去重；打开分享面板或申请分享令牌不能声称实际发送、送达或被他人阅读。未能验证的“转发”证据不启用该分值。
- 收藏、主动咨询、测算成功由各自服务端事实确认；测算是估算成功，不得伪装为正式报价、支付或签约。
- 旧咨询业务事实在 Go 线索退为来源后，必须改为可验证的持久业务事实引用；不能继续用 CRM 不再更新的旧 `customer_leads.status` 判断当前需求是否有效。
- 员工自访、预览、异常、重复、可识别内部流量按规则排除。账号身份不是永久替代需求类型的过滤器（D03）。
- 明确“7 天无行为后每日衰减”按最近有效行为计算，每个计算日一次，不因查询次数重复扣分；窗口移出的贡献自然移出。规则调整不重写历史获客、归属和成交。
- 多内容 owner 的证据不得通过评分聚合扩大顾问权限；分数计算范围与销售动态展示范围分别校验。

### 9.3 影子期与启用条件（待确认 D06）

推荐先运行至少两周候选观察，主管确认后才进入正式销售线索。原稿“抽查 50 条、60% 值得联系”仅保留为探索参考，不能单独证明可以全自动。

影子期必须展示各来源/身份/分数段的：候选量、可联系率、联系成功率、真实需求确认率、重复与误分率、销售处理积压、拒绝联系数量。样本不足时报告数量与不确定性，不强行宣布通过。

若 D06 选择后续自动化，正式开启前另记录批准人、规则版本、适用渠道、阈值、当日新增上限、负责人接收上限、异常停止条件；只对可联系、无冲突、无拒绝联系、无既有需求的候选启用。自动创建、自动分配、超时回收独立开关，停用不会删除历史。

## 10. 成交、金额与经营统计

### 10.1 业务范围与成交事件（待确认 D09、D10）

项目已有报告、会员、模板、设计/造价咨询等场景，但代码功能不能证明实际签约主体和经营收入范围。D09 先由用户明确人工设计、造价、施工承包、渠道转介及其他服务的实际经营与签约主体，再决定哪些纳入首期漏斗。推荐只把本平台实际签约的人工服务计入平台销售成交；合作方签约转介单独统计成果，不能计为平台合同额或收入。报告/会员/模板按现有产品订单独立展示，不因出现“建房”字样就假定平台承包施工。

对 D09 最终确认纳入的人工服务，推荐以有效合同签署并经主管核实为成交；定金记录为独立的收款/签约推进事实。若选择合同或有效定金任一即可成交，必须保留 `成交依据=合同/定金`、业务类型和时间，且同一需求随后补签合同不重复计成交（D10）。不适用合同/定金的服务或转介成果，需在 D09、D10 确认中另写达成事件，不能套用不存在的合同。

每条成交至少明确：需求、业务类型、成交依据、业务发生日、主管确认日、金额口径、凭证引用、当时负责人。全屋造价预算不能作为设计合同金额；报价、合同、定金、已收款、确认收入分别命名。

退款、退定、合同撤销保留调整事件，不删除旧成交；是否关闭需求或恢复推进经主管处理。订单退款状态以订单业务事实为准，不由 CRM 手动状态覆盖。

### 10.2 统计单位与日期

| 指标 | 修订口径 |
| --- | --- |
| 来源事件数 | 咨询、关系、分享等各类去重事件数；不是客户总数 |
| 去重联系人/客户业务档案/需求数 | 各自单列，依 D01、D12 的最终对象定义命名，不混为“客户数” |
| 新增正式销售线索 | 首次进入可承接销售线索的独立需求；候选、合作、重复咨询、回收重领不新增计数 |
| 线索转客户 | 明确发生资格转换的事件；手动直接报备和历史纳管单列，不补造前序线索 |
| 线索转客户率 | 同一新增线索批次中在固定观察窗内转客户的数量 / 该批次合格纳入分母的线索数；另列未核实数 |
| 当前阶段分布 | 当前各阶段的在办需求存量，属于快照 |
| 阶段转化 | 同一需求实际进入阶段的历史事件；跳过阶段不补造经过记录，单列跳转 |
| 首次响应 | 从可承接且分配成功到首次人工尝试；另列从生成到分配等待时长 |
| 首次有效联系 | 从可承接且分配成功到首次成功沟通；未接不算成功，另报未联系和未成功比例 |
| 内容效果 | 具备可信触点证据的访客、候选、正式线索、客户、成交分别统计；未知归因单列 |
| 合作线索 | 独立分母；分类纠错以明确调整事件反映，不伪装新获客 |
| 实际订单/收款/退款/收入 | 各现有权威业务系统提供的事实；不以概率或 CRM 阶段替代 |

首次响应、有效联系不能只对已完成者取中位数而隐藏大量未处理；应同时展示样本数、未完成量及超时率。

批次统一使用首次进入正式线索的时间；时间范围为北京时间的左闭右开区间。7/30/90/180 天观察窗可作为报表选项，必须显示观察截止日；未到完整观察期标为未成熟批次，不能与完整批次直接比较优劣。

来源归因保存首次获客与最近触点；各素材可显示参与贡献，但涉及“独占归因”的合计报表必须采用同一确定规则，不把一个成交完整计给多个人后相加。渠道贡献不自动等于佣金归属。

### 10.3 销售预测（待确认 D11）

推荐首期先提供阶段分布、下一步和预计成交月份，待真实签约金额与历史结果可对账后再展示概率加权预测。

若选择首期展示：每个需求必须有对应业务类型的预计签约金额、币种/单位、预计成交月份和概率来源；用单值金额，不默认取预算区间中点。阶段概率为试算参数，显示规则版本，不能与行为分数混用。

只对未成交、未关闭且符合本期预测纳入条件的需求求和；暂缓默认从近期在办预测中单列，到恢复及确认预计月份后再纳入，已成交不能同时计入未成交预测。概率加权金额显示为“试算”，不能叫当月实际收入。

## 11. 页面、角色与日常使用

### 11.1 日常页面

- **线索**：待分配、待联系、核实中、逾期、联系信息异常；显示渠道、分享人、最近动态、当前接待人、下一步。行为候选独立标签/入口，不混入正式线索徽标。
- **客户**：联系人和关系、当前需求与阶段、需求历史、保护到期、回访承诺、来源、方案/报价与成交凭证。
- **我的待办**：联系尝试、有效回访、资料补齐、阶段停留等分别标原因；同一对象多个原因合并展示，不把一次提醒算多人次线索。
- **客户公海**：按允许公开的信息范围展示，认领后才能访问完整资料。现有销售公海规则不用于合作和明确拒绝联系对象。
- **主管待处理**：待分配、疑似重复、分类核实、离职交接、归属争议、成交/归档审批、公海回访、同步失败。
- **内容效果**：访客、素材、传播贡献与候选；已有线索/客户可按权限跳转。
- **设置**：账号绑定、授权、营业日历、评分/自动化开关、同步配置和口径说明。

### 11.2 权限与通知

1. 顾问只处理授权给自己的需求；主管按现有授权范围核实分配。渠道账号不因没有企微员工绑定就失去既有合法报备能力。
2. 内容作者、分享人、原负责人、家庭成员关系都不自动授予当前客户详情权限；外部转介绍人不获得客户电话、需求或成交详情。
3. CRM 动态接口先核实当前客户/需求权限，再映射可展示的 tracking 与客服事实；不能直接借主管 tracking 权限返回客户跨范围轨迹。
4. 转交/回收后原顾问权限即时变化，历史贡献可在其授权统计范围内保留，不保留完整联系方式访问权。
5. 新分配、客户主动请求、到期、交接、回收是可行动提醒；普通浏览合并为摘要，避免用“每天最多一条”吞掉紧急任务。
6. 同一事件通知幂等；站内生成、企微推送成功、推送失败分别记录，不能以任务已创建声称顾问收到。

| 角色/关系 | CRM 需求详情与综合时间线 | 传播效果 |
| --- | --- | --- |
| 当前负责人 | 仅其被授权的独立需求及必要联系人 | 仍需相应内容/统计权限 |
| 主管 | 仅其管理授权范围 | 仅其统计授权范围 |
| 内容 owner、员工分享人、历史负责人 | 不因传播或历史身份取得当前详情权限 | 可见授权范围的脱敏贡献，不通过可识别客户列表绕过权限 |
| 家庭联系人、外部转介绍人 | 不因关联取得内部后台权限 | 不因转介绍取得内部客户/成交详情 |

已有客户跳转必须重新核实上述 CRM 权限；有传播统计可看不代表可以打开客户档案。

## 12. 系统职责、可靠性与删除边界

### 12.1 唯一业务权威

| 模块 | 负责 | 禁止竞争的状态 |
| --- | --- | --- |
| Java CRM | 业务主档、线索处理、需求资格/阶段、负责人、保护、公海与审批 | Go 旧线索不再管理另一套销售状态 |
| Go 客服采集 | 持久保存用户明确提交及来源、可靠投递 | 不直接凭草稿判定合格客户或成交 |
| Go tracking | 已授权的行为事实、可解释评分、候选、传播链与动态查询 | 不直接覆盖 CRM 当前归属、保护与关闭结果 |
| 订单/支付/报告等现有模块 | 各自交易与交付事实 | CRM 不能手工制造支付成功、报告交付或退款成功 |
| React/小程序 | 按权限采集与呈现、发起显式业务动作 | 不相信浏览器传来的分享 owner、成交状态或任意客户 ID |

### 12.2 所有来源共用的处理合同

1. 入口有稳定事件/来源标识、发生时间、接收时间、身份与归因证据；来源请求与身份必须由服务端验证。
2. 接收成功的含义是已经持久保存。CRM 未接收时返回“已提交，处理中”，不能显示已分配或已转客户。
3. 持久待投递记录包含目标、幂等键、版本/游标、失败原因、重试和确认结果；不强制引入新消息中间件。
4. CRM 接收时在同一业务事务内校验重复、联系限制、既有归属/资格并保存结果；人工与自动同时处理同一需求只能产生一个正式转换。
5. 超时、确认丢失、服务重启后重试返回原结果；不能重复开档、重复起保护、重复通知或倒写旧版本。
6. 已存在关联时追加来源，已拒绝/关闭/合作时返回明确处理结果，不把这些情况当接口失败无限重建。
7. Go 旧线索转来源后，状态不得继续承担 CRM 当前事实。CRM 无效、恢复、纠错必须能影响后续候选判断；历史无效过滤也要处理已同步记录的主管核实，不能只跳过未来同步便声称治理完成。
8. 来源字段升级用版本化补传/指定回填，明确哪些老记录补字段、哪些不重放新建。不能以“永远不改变 source_hash”导致新增归属永远无法同步，也不能批量重放抢归属或续保护。

### 12.3 删除与联系限制

行为删除清除其对应的 tracking 事实及 CRM 中复制的行为摘要/快照，传播身份引用按权限与删除范围处理；保留必要业务事实时不继续夹带已删除行为明细。

身份/行为删除、客户业务归档、明确拒绝联系、交易保留是不同动作。业务联系方式是否保留及多久沿用已制定的数据政策；若尚无明确政策，上线前补齐相应治理规则，不用本稿替代法律或隐私政策评估。

删除期间停止该身份的候选投递并记录不可重放状态；重试、全量重算、旧快照、异步队列不得把已删除事实重新导回 CRM。匿名关闭采集不伪造空白历史，未授权的行为不进入评分。

## 13. 历史切换与回退

1. 在库副本生成预览：来源数、联系人/主档/需求数、疑似重复、当前归属、保护、阶段、跟进、附件、明确拒绝和已成交记录。
2. 原编号、合法归属、有效保护到期和历史成交保留；历史活跃客户首次纳管沿用已确认的主管核实、一次性起算规则，不把所有旧记录批量新保护。
3. 旧 `converted` 不直接当已确认成交；先分清旧线索转化、真实业务成交与对应凭证。旧 `legacy`、`archived` 不因不等于 `pending` 自动计为合格客户。
4. 无法可靠映射阶段的旧记录进入原阶段待校正，保留原值；不从最近一个“报价”字样推断已进入签约。
5. 批量回填不刷新有效联系、资格转换、阶段进入和保护时间；不以新评分规则重算历史分享归属、提成或成交。
6. 按客户批次对账来源、跟进、附件和金额引用；新增身份分流列、Java 迁移和旧客户端兼容另做执行验证，不能把分支测试当生产迁移完成。
7. CRM 新入口可以完整承接后，才把旧页改为来源查询；更新旧《移交约定》中“加企微才移交”的入口规则。未加企微但已有合法电话/联系关系的线索同样在 CRM 承接，不再卡在不可写旧页。
8. 回退保留旧 ID 映射和来源，停止新自动化及新写入链路，经对账选择恢复哪一个业务写入口，禁止两套同时恢复可写。回退不撤销已经发生的客户联系、主管决定或成交事实。
