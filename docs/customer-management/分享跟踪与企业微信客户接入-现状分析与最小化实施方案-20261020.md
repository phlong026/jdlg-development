## 0. 结论先行

### 0.1 五个判断

1. **两条业务都不是从零开始，但都只完成了“前半段”。**
   - 分享跟踪：采集、会话轨迹、素材维度、渠道维度、意向规则、权限与删除治理做得相当完整，属于“可观测系统”。
   - 企业微信导入：能全量拉取“员工—外部联系人”关系并建档，属于“关系同步器”。
   - 但“分享访客 → 判断意向 → 进入 CRM 持续跟进”和“企微客户 → 补全画像 → 分配跟进”这两个**业务闭环**都没有真正闭合。

2. **功能一（分享 → 跟踪 → 意向 → CRM）当前是断的，断点不在采集，而在跨系统边界。**
   - CRM 桥接开启后，分享页的“转为销售线索”被硬编码返回 `409 客户已统一纳管`（[share_tracking_lead.go:171-174](../../service/route/share_tracking_lead.go#L171-L174)）。
   - CRM 没有“访客/行为证据 → 客户”的接入接口；`/ingest/miniprogram` 只接受姓名、电话、微信、摘要等基础字段，且 `externalId` 必须是数字 lead id（[CustomerWorkflow.java:47-55](../../customer-management/phase1/src/main/java/cn/iyque/phase1/CustomerWorkflow.java#L47-L55)）。
   - CRM 客户详情只有一行“来源摘要”，没有小程序访问轨迹；轨迹组件只挂在线索工作台（[customerLeads.tsx:730](../../background/src/pages/customerLeads.tsx#L730)），而 CRM 开启后线索页对销售只读、`crm_only` 账号甚至被重定向离开（[ProtectedRoute.tsx:10](../../background/src/component/ProtectedRoute.tsx#L10)）。

3. **分享跟踪模块本身“齐全度较高”，但业务覆盖不齐。**
   - 基础设施：入口令牌、分享链、事件白名单、会话/素材/渠道视角、意向规则版本、人工修正、删除墓碑、权限隔离，均有实现。
   - 业务缺口：**预算页只到“打开表单”，没有金额/参数/测算成功的内容级归因**；效果图详情的“收藏”走的是 `/like` 而不是可确认的收藏回执；效果图详情的手机号留资按钮绑定了未定义方法；**匿名访客永远没有意向等级**，导致“匿名高意向池”实际为空；朋友圈首次分享没有令牌；分享令牌 30 天、原始事件建议保留 90 天，难以覆盖乡墅长周期。

4. **企业微信导入“能导入”，但导入的是骨架，不是可销售的客户画像。**
   - 当前只取 `external_userid / name / avatar / type` 和 `followed_users(userId, createTime, state)`（[WecomGateway.java:16-17,40-52](../../customer-management/phase1/src/main/java/cn/iyque/phase1/WecomGateway.java#L16-L52)）。
   - 企微返回的标签、备注、手机号、unionid、添加方式没有落库；`iyque_customer_info` 里明明有 `tagIds/addWay` 字段却没有赋值（[IYQueCustomerInfo.java:39-46](../../customer-management/src/main/java/cn/iyque/domain/IYQueCustomerInfo.java#L39-L46)、[ImportService.java:63-71](../../customer-management/phase1/src/main/java/cn/iyque/phase1/ImportService.java#L63-L71)）。
   - 手机号通常要顾问手工补录（[phase1/README.md:59](../../customer-management/phase1/README.md#L59)），因此“按手机号去重/合并”在导入时基本失效。

5. **“对标飞鱼 CRM”需要先纠正对象。**
   - 公开可核验的“飞鱼 CRM”是**巨量引擎（字节）的广告线索管理与外呼工具**，不是企业微信 SCRM；公开文档/帮助中心未见原生企微通讯录、外部联系人、会话存档能力，也没有分享传播追踪（企微场景通常通过第三方 iPaaS 接入）。
   - 它能对标的是“线索池、分配、去重、回收、跟进、权限、API”这一段；不能对标“企微导入”和“分享跟踪”。把飞鱼当整体对标，会得出错误结论。

### 0.2 一句话回答三个问题

| 问题 | 结论 |
|---|---|
| 1. 现有代码能否实现这两个功能？还缺什么？ | **能实现“采集、查看、判断”的大部分；不能实现“自动进入 CRM 并持续跟踪”的闭环。** 缺 1 条访客→CRM 的写入通道、1 条 CRM→轨迹的读取通道、1 套跨端身份映射，以及企微导入的画像字段/去重。 |
| 2. 分享跟踪模块是否齐全？前置数据能否跟踪客户行踪？ | **模块齐全度中上，业务覆盖中等。** 能回答“谁分享、带来多少访客、看了哪些页面/素材、停留多久、是否登录/收藏/咨询”；不能可靠回答“具体哪份预算、哪张效果图、是否加企微、是否成交”，也不能跨设备/长周期还原同一个人。 |
| 3. CRM 配置/接口能否承接两条业务？对标飞鱼如何？ | **能承接“基础客户档案 + 跟进 + 保护期/公海”，不能承接“行为证据、意向、分享链、身份解析”。** 飞鱼可借鉴线索池/分配/去重/回收/权限，但不能照搬其广告线索模型。 |

## 2. 现状架构：四条链路，两个 CRM

### 2.1 四条链路

```text
A. 分享跟踪
小程序（st 分享令牌）
  → Go /api/v1/miniprogram/tracking/{entry,shares,events/batch}
  → tracking_records（visitor/session/share/page_view/event/business）
  → 管理后台“分享访问记录”（访客/素材/渠道/意向规则）
  → 仅 CRM 关闭时：Go customer_leads → outbox → Java CRM

B. 小程序咨询/线索
小程序客服 handoff_human
  → Go /customer-service/consultation-requests
  → customer_leads + customer_service_events
  → crm_sources.go 轮询 → Java /ingest/miniprogram
  → CRM pending 客户（无归属）

C. 企业微信客户
企微回调 / 全量 sync
  → Go wecom_event_inbox 转发（回调）
  → Java WecomController → ImportService → iyque_customer_info + crm_customer
  → CRM 客户档案 / 跟进 / 保护期 / 公海

D. 两套 CRM
统一后台 /api/v1/management/crm/* → Go 签名代理 → Java phase1（当前实际使用）
customer-management/src + frontEnd/pc/mobile → 完整 iyque SCRM（未接入统一后台）
```

### 2.2 关键事实：当前接入的是 phase1，不是完整 iyque

- `customer-management` 仓库里有两套东西：
  - `src/main/java/cn/iyque/**`：完整源雀 SCRM，含客户公海、标签、群发、会话存档、活码等（约 378 个 Java 文件）。
  - `phase1/src/main/java/cn/iyque/phase1/**`：19 个 Java 文件、约 1,384 行，是统一后台实际代理的客户管理。
- phase1 的 `pom.xml` 只编译 `cn/iyque/phase1/**` 和少量复用类，不编译上游控制器（[phase1/pom.xml:20-26](../../customer-management/phase1/pom.xml#L20-L26)）。
- 因此：**README 里看到的 iyque 全量能力，不等于统一后台“客户管理工作台”的能力。** 当前工作台的标签、批量导入、SOP、群发、会话存档等能力并不在 phase1 中。

> 这一点直接决定问题 3 的答案：不是“CRM 功能不够”，而是“当前接入的是最小 CRM，完整 CRM 没有接进来”。

### 3.2 分享令牌与传播链

- 分享令牌由 `prepareShare` 在 `onShareAppMessage` 的 promise 链中创建，追加 `st` 参数（[tracking/index.ts:121-143,203-210](../../miniprogram/miniprogram/utils/tracking/index.ts#L121-L210)）。
- 服务端 `Share` 记录包含 `Sharer / Session / Content / Version / Parent`（[types.go:157-169](../../service/tracking/types.go#L157-L169)）；重新分享可形成 `parent_share_id` 链。
- 渠道视角能按分享者聚合“发起分享 / 带来访客 / 其中高意向 / 已转线索”（[share_tracking_channels.go:61-69](../../service/route/share_tracking_channels.go#L61-L69)、[share_metrics.go:65-76](../../service/tracking/share_metrics.go#L65-L76)）。
- **传播链只走通一半**：能看“谁分享、带回多少人”，不能看“分享给了谁、下游是谁”；会话只标“通过分享进入”，UI 不展示 `share_id`，也不回跳分享人（[details.tsx:42](../../background/src/pages/shareTracking/details.tsx#L42)）。
- 三个已知损耗：
  1. 朋友圈无异步完成回调，**首次朋友圈分享必然无令牌**（[tracking/index.ts:212-221](../../miniprogram/miniprogram/utils/tracking/index.ts#L212-L221)）。
  2. 卡片分享 1,800ms 超时回退；超时后 `prepareShare` 仍在跑，可能“有分享记录、但发出去的卡片无令牌”。
  3. 分享令牌 30 天过期（[service.go:305](../../service/tracking/service.go#L305)）；乡墅客户 30 天后回看旧分享，归因丢失，退化为直接访问。

### 3.3 访客实际被采集了什么

| 页面路径 | ✅ | `route_key` + 页面标题 |
| 素材/版本 | 🟡 | 效果图详情有 legacy content + version；首页/预算/广场只有 route |
| 停留时长 | ✅ | 10s 心跳、可见区间并集；>15s 采样缺口记 `sampling_gap` |

| 手机号/unionid/openid | 🔴 | 追踪载荷不含这些字段（[types.go:170-199](../../service/tracking/types.go#L170-L199)）；只能靠登录账号 `u:<id>` 反查 |
| 加企微 | 🔴 | 没有把“分享访客”和“企微 external_userid”连起来的通用通道；只有报告/模板下载的局部票据 |

### 3.4 身份识别：只有“同设备 30 分钟内登录”能合并

- 匿名键：`a:<client_instance>`，同一安装号的随机标识。
- 登录后：`u:<users.id>`。
- 服务端只在以下条件把匿名会话升级为登录身份：同一 `client_instance`、30 分钟内、旧会话匿名、新会话登录（[service.go:178-196](../../service/tracking/service.go#L178-L196)）。
- 跨设备、隔天、超过 30 分钟、不同入口，都不会自动关联。
- 这意味着：**“客户行踪”在当前数据模型里是“设备/短会话级”，不是“自然人级”。** 对乡墅这种长周期、多人决策、微信+企微+电话多触点的业务，单靠这套身份键不够。

### 3.5 意向判断：规则完整，但覆盖太窄

默认规则 `followup-v1`（[rules.go:82-84](../../service/tracking/rules.go#L82-L84)、[intent-rules.md:8](../share-tracking/intent-rules.md#L8)）：

- 中意向：近 30 天 ≥2 个独立会话 **且** ≥1 次服务端确认收藏。
- 高意向：近 30 天 ≥1 次服务端确认的咨询/预约/报价成功。
- 低意向：有有效访问，但不满足以上条件。
- 匿名：**永远是 `unknown`**（[query.go:590-605](../../service/tracking/query.go#L590-L605)）。

这带来三个业务后果：

1. **只浏览、不收藏/不咨询的分享访客，即使看了 20 个页面，也只是“低意向”。** 对“分享获客”场景，这个门槛过高。
2. **匿名访客没有等级**，所以后台的“匿名高意向池”（`identity=anonymous&intent=high`）按当前代码会返回空列表；这与该按钮的文案承诺不一致（[shareTracking.tsx:51](../../background/src/pages/shareTracking.tsx#L51)）。
3. **预算测算完成不是业务事实**：`aicost` 的测算只写本地 storage，没有服务端成功事件（[aicost.ts:344-353](../../miniprogram/miniprogram/pages/aicost/aicost.ts#L344-L353)），所以“完成预算”不会提升意向。

### 3.6 进入 CRM：当前是死路，不是“还没做”

| 场景 | 当前结果 | 证据 |

| CRM 未开启 | “转为销售线索” → `customer_leads`（source=`share_tracking`）→ 线索工作台可跟进 | [share_tracking_lead.go:160-181](../../service/route/share_tracking_lead.go#L160-L181) |

**为什么 409 是设计而非 bug：** 现有设计把 CRM 当唯一客户写入口，把 Go 线索工作台降级为“历史查询”。这个方向本身合理，但缺少替代通道，导致“高意向但未主动咨询”的分享访客无法进入 CRM。

**目前唯一能自动进 CRM 的新客通道**是小程序主动咨询：`/customer-service/consultation-requests` → `customer_leads` → outbox → `/ingest/miniprogram`（[customer_service.go:163-208](../../service/route/customer_service.go#L163-L208)、[crm_sources.go:19-77](../../service/route/crm_sources.go#L19-L77)）。这条通道要求客户主动留资/转人工，不能覆盖“沉默高意向”。

### 4.3 归属、去重与保护期

- **归属**：新建客户时，取最早添加关系的员工为 `ownerId`（[ImportService.java:52-54](../../customer-management/phase1/src/main/java/cn/iyque/phase1/ImportService.java#L52-L54)）。
- **不按手机号/unionid 合并**：`snapshot()` 只用 `sourceCustomer("wecom", externalId)` 或 `findById(externalId)`；找不到就新建。
- **生命周期**：导入客户一律 `pending`，`CustomerProtection.inPool()` 明确不把 `pending` 视为公海（[CustomerProtection.java:18-20](../../customer-management/phase1/src/main/java/cn/iyque/phase1/CustomerProtection.java#L18-L20)）；需要补齐 5 项报备资料后才起 90 天保护（[CustomerService.java:62-68](../../customer-management/phase1/src/main/java/cn/iyque/phase1/CustomerService.java#L62-L68)）。
- **重跑**：全量同步没有断点游标；进程重启会把 `running` 置 `failed`，靠 30 分钟周期重跑（[SyncService.java:19-21,68](../../customer-management/phase1/src/main/java/cn/iyque/phase1/SyncService.java#L19-L21)）。
- **规模**：按员工逐个 `listExternalContacts`，再逐客户 `getContactDetail`；没有批量接口/限速/分片，客户量大时容易触发企微频率限制或超时。

### 4.4 运营入口与权限

- “发起同步”只对客户主管（CRM `role=admin`）可见（[customerManagement.tsx:40,77](../../background/src/pages/customerManagement.tsx#L40-L77)）。
- “账号与权限”只对平台管理员可见；要先把后台账号绑定到企微员工，否则顾问登录后看不到企微自动接入的客户（[customerManagement.tsx:107](../../background/src/pages/customerManagement.tsx#L107)、[AccessPanel](../../background/src/pages/customerManagement.tsx#L211)）。
- 分配/交接：单客户 `transfer`（主管）、公海 `claim`（顾问）、待办/逾期队列都有；没有批量分配、没有按来源/地区/负载的自动分配规则。
- 结论：**“导入 → 分配 → 跟进”能走通，但依赖平台管理员和主管先完成账号绑定/同步；普通顾问不能自助。**

### 5.3 六个关键缺口（按业务影响排序）

1. **预算页没有内容级归因，且分享落页与卡片不一致。**
   - 卡片写“XX 市 XX ㎡ 造价 XX 万”，点开是空白表单；结果页被排除采集。
   - 这会同时伤害体验和归因：客户以为能看报价，销售以为客户看了报价，实际都没有。

2. **效果图详情的主转化动作不在链路里。**
   - “收藏”走 `/like`，不产生 `ConfirmFavorite`；手机号按钮 `onEnterpriseWechatPhoneAuth` 在 `templatesquaredetails.ts` 中未定义（只有 `generatedetails` 有），点击无反应。
   - 这意味着效果图页最强的“收藏 + 留资”两个信号都丢失。

3. **匿名访客没有意向等级，“匿名高意向池”实际为空。**
   - 代码只对非 `a:` 计算 low/medium/high（[query.go:590-605](../../service/tracking/query.go#L590-L605)）。
   - 后台按钮筛选 `identity=anonymous&intent=high`，结果为空，与文案“近30天意向升至高但尚未留资”矛盾。
   - 对分享裂变场景，这是致命的：大部分接收者不会立刻登录。

4. **首页 audience=neutral，纯首页访客的 CustomerShare=0。**
   - `routes.json` 中 `pages/index/index` 的 `Audience` 为 `neutral`（[routes.json](../../service/tracking/routes.json)）。
   - 灰区转化要求 `customerShare >= 0.7`（[share_tracking_lead.go:56-59](../../service/route/share_tracking_lead.go#L56-L59)）；只逛首页的已登录但未选身份访客，永远过不了这个门槛。

5. **分享令牌 30 天、原始事件建议 90 天，覆盖不了乡墅长周期。**
   - 30 天后旧分享退化为直接访问；90 天后原始明细不可查（汇总 180 天）。
   - 乡墅从了解到签约常超过 3-6 个月；“客户行踪”需要更长窗口或至少保留关键触点摘要。

6. **“静默同意”与文档口径冲突。**
   - `refreshConfig()` 对“从未选择”的用户自动 `setConsent(true)`（[tracking/index.ts:47-50](../../miniprogram/miniprogram/utils/tracking/index.ts#L47-L50)），而文档写“独立同意默认关闭”。
   - 这是合规风险，不是技术 bug。**生产已开启采集（2026-10-20 实测），需要立即由法务/隐私负责人确认**，口径不通过时可先在配置里关闭采集。

- 模板详情 `onShareAppMessage` 依赖返回值里的 `success` 回调记 `POST /templates/:id/share`（[templatesquaredetails.ts:278-288](../../miniprogram/miniprogram/pages/templatesquaredetails/templatesquaredetails.ts#L278-L288)）；微信官方已不保证分享成功回调，依赖它统计“分享成功”不可靠。
- 该接口还把 `UserID` 硬编码为 `0`（[template.go:1032](../../service/route/template.go#L1032)），所以 `template_shares` 既没有分享人，也不稳定。
- 但 `JDLG` 的分享跟踪有独立的 `share` 记录和 `share_intent` 事件（[service.go:294-310](../../service/tracking/service.go#L294-L310)），后台“分享访问记录”用的是这一套；**不要把 legacy `template_shares` 的失真等同于整个分享跟踪失效**。Claude 的报告因为其基线没有 tracking，把两者混在一起了。

### 6.1 当前 CRM 的领域模型（phase1）

| `crm_followup` | 跟进 | 有效/无效、续期、附件；无来源回链 |

| `crm_event/crm_sync_run` | 回调事件/同步任务 | 有重试；无全量断点 |

### 6.3 三个“接不住”

#### 接不住 1：分享访客没有写入通道

- `ingest` 的 `externalId` 必须是 1-19 位数字（[CustomerWorkflow.java:48](../../customer-management/phase1/src/main/java/cn/iyque/phase1/CustomerWorkflow.java#L48)），而 tracking 访客键是 `u:<id>` / `a:<id>`。
- 没有 `visitor_key / session_id / share_id / intent_level / evidence` 字段。
- 现有 outbox 也没有把 `intent_level / session_no / source_task_no` 传给 CRM（[crm_sources.go:61](../../service/route/crm_sources.go#L61)），所以连“这条 lead 原本是高意向”都会丢；CRM 新客户 `intent` 默认是 `medium`（[Models.java:17](../../customer-management/phase1/src/main/java/cn/iyque/phase1/Models.java#L17)）。
- `ingest` 对已存在客户只更新 `crm_source`，不更新姓名/电话/需求等客户字段（[CustomerWorkflow.java:48-50](../../customer-management/phase1/src/main/java/cn/iyque/phase1/CustomerWorkflow.java#L48-L50)）；后续补资料不会自动收敛到客户主档。
- 结果：CRM 只知道“有一个小程序 lead”，不知道“他看了什么、为什么高意向、是谁分享的”，甚至不知道 lead 的原始意向等级。

#### 接不住 2：CRM 客户详情看得到“来源摘要”，看不到“轨迹”

- `CustomerDrawer` 会通过 `WorkflowDetails` 渲染 `crm_source`：来源类型、姓名/电话、`externalId`、提交人、渠道、摘要（[customerWorkflow.tsx:51-52](../../background/src/pages/customerWorkflow.tsx#L51-L52)）。
- 所以 CRM **能看到**一段行为摘要（如果 ingest 的 `summary` 里带了）；但看不到会话、页面明细、停留时长、素材/图片、意向证据。
- `CustomerLeadTrail` 只在线索详情；CRM 客户详情没有（[customerLeadTrail.tsx:8-42](../../background/src/pages/customerLeadTrail.tsx#L8-L42)）。
- 结果：销售能看到“他来自分享、摘要说近30天到访 N 次”，但不能自己展开验证“上周看了哪 3 张效果图、停留多久”。

#### 接不住 3：身份没有统一主键

现有映射是碎片化的：

| 映射 | 位置 | 覆盖范围 |
|---|---|---|
| 平台账号 ↔ CRM 账号 | `management_crm_link` | 员工登录 |
| 访客 ↔ CRM 客户 | `tracking crm` 记录（`identity-links`） | 单访客、人工、需 `can_crm` |
| 来源外部 ID ↔ 客户 | `crm_source` | lead id / external_userid |
| 手机号 ↔ 小程序账号 | `user_identities` | 仅手机号 |
| 小程序账号 ↔ 企微 external_userid | `enterprise_wechat_bind_tickets` / `report_wecom_tickets` | 仅模板下载/报告场景 |
| 企微 external_userid ↔ 员工 | `iyque_customer_info` | 关系 |

缺一张统一的 `customer_identity`（`customer_id, kind, value_hash, verified_at, source`）和解析/合并 API。没有它，“同一个人小程序咨询 + 加企微 + 再分享”会被拆成 2-3 份档案。

### 6.4 配置能否满足？

| 配置 | 是否具备 | 说明 |
|---|---|---|
| CRM 桥接（URL/KEY/AUDIENCE/KEY_ID） | ✅ | HMAC-SHA256、±60s、nonce、审计 |
| 企微客户联系（corp/secret） | ✅ | 全量+回调 |
| 企微回调（token/aes） | ✅ | 与 Go 事件收口共存 |
| 角色/数据范围（platform_admin/crm_only/admin/staff） | ✅ | 单企业；无部门/多租户；CRM 侧只有 `admin/staff`，客户主管=`admin`，账号管理在平台侧；没有“店长/城市负责人”等中间层 |
| 跟踪权限（tracking_access 五项能力） | ✅ | 独立授权；默认不授权 |
| 小程序素材授权 | 🟡 | 无 UI；需 DBA 手工写 `tracking_access` |
| 来源接入（@source） | 🟡 | 共享密钥；`submittedBy/channel` 可被持有密钥方伪造 |
| 字段级权限/脱敏 | 🔴 | 只有 admin/staff + 本人/公海；无字段级 |
| 批量导入/分配 | 🔴 | 无文件导入、无批量分配、无自动分配规则 |
| 多企业/多租户 | 🔴 | 单库单实例；`crm_*` 无 tenant |

**结论：配置项齐全，但“能配”不等于“好配”。** 上线需要 6 类环境变量 + 3 张授权表 + 账号绑定 + 跟踪授权；没有一键自检，半配置状态很容易出现“同步成功但销售看不到”“授权了但列表为空”。

## 7. 对标飞鱼 CRM：先辨对象，再谈差距

### 7.1 飞鱼是谁

公开可核验的“飞鱼 CRM”是**巨量引擎（字节跳动）旗下的广告线索管理与外呼工具**，官网 [feiyu.oceanengine.com](https://feiyu.oceanengine.com/)，App 开发者为 Ocean Engine（包名 `com.bytedance.ad.crm`）。它：

- 定位在广告投放之后：线索承接 → 分配 → 外呼 → 标记 → 深度转化回传广告模型。
- 是公有云 SaaS，官方称免费；主要服务线索型/电销型行业。
- **不是企业微信 SCRM**：公开文档/帮助中心未见原生企微通讯录、外部联系人、会话存档、群发、朋友圈能力；企微场景通常通过第三方 iPaaS 接入。
- **没有分享传播追踪**：官方 FAQ 明确，经分享落地页/站外落地页进入的属“外部线索”，拿不到客户 ID，即没有访客级追踪。
- 企微客户导入/同步：公开能力未见原生同步；通常通过 S-HUB、尘锋、探马等第三方 iPaaS 把飞鱼线索推到 SCRM。

> 因此：如果你的“对标”是“企微私域 + 分享获客”，飞鱼不是同类产品；它只能对标“线索池与销售跟进”这一段。若你实际指的是另一款同名企微 CRM，需要重新确认对象。

### 7.2 能力对比

| 能力 | 飞鱼 CRM | 当前自建 | 判断 |
|---|---|---|---|
| 广告线索自动落入 | ✅ 巨量/抖音/多账户 | 🔴 无广告平台接入 | 飞鱼强；自建不需要（除非投广告） |
| 线索池/公海 | ✅ 领取/回收/工作量上限 | 🟡 90 天保护期 + 公海认领 | 自建规则更适合乡墅长周期；可借飞鱼“行为+结果”回收条件 |
| 线索分配 | ✅ 条件→员工/组→轮流/补齐→优先级→兜底→溢出补分 | 🔴 仅人工交接/公海认领 | **最值得借** |
| 去重 | ✅ 手机/微信、1-366 天、账户内/跨账户、合法转化例外 | 🔴 仅手动报备按手机号拦截；导入不合并 | **最值得借** |
| 外呼/录音/质检 | ✅ 中间号、双向回呼、转写、智能标签 | 🔴 无 | 自建不必重造；可接第三方 |

| 企微客户管理 | 🔴 公开能力未见原生 | ✅ 关系同步/回调/公海/保护期 | **自建优势** |
| 分享/访客追踪 | 🔴 无 | ✅ 入口/会话/素材/渠道/意向 | **自建优势** |
| 小程序/订单/交易 | 🔴 无 | ✅ 现有业务系统 | 自建优势 |

| 开放 API | ✅ 推送规则+拉取 API+签名+重试 | 🟡 内部 HMAC 桥；无公开 API | 飞鱼强；自建按需 |

### 7.3 可借鉴 / 不可照搬

**可借鉴：**

1. **去重规则要显式定义五件事**：匹配键（手机/微信/unionid）、时间窗、账户范围、例外（合法转化/保护中客户）、是否回溯。飞鱼把“改规则不回溯”写在文档里，避免运营和财务打架。
2. **分配拆成六段**：条件 → 对象 → 策略（轮流/按量补齐）→ 优先级 → 兜底 → 溢出补分。比“按员工轮询”健壮。
3. **回收用“行为 + 结果”双条件**：例如“获得线索后 N 天未添加商机”且/或“N 天未有效联系”；回收前 1 天提醒；员工可主动退回。比单一 90 天倒计时更防占坑。
4. **跟进状态由行为自动推导**：打电话、写跟进、预约回访任一动作即“跟进中”；转商机/无效即“跟进结束”。减少销售手填。
5. **字段级权限 + 操作日志**：手机号明文/掩码、数据范围（本人/组/全部）、导出二次验证。

**不可照搬：**

- 广告平台耦合、免费外呼、无效线索返款、2 年留存、无企微/无分享。
- 飞鱼的“线索”是广告线索，不包含小程序行为；直接把它的阶段套到乡墅业务，会丢失“内容兴趣/方案/预算”这些关键信号。
- 飞鱼没有“90 天保护期”概念，只有领取/回收；乡墅的报备保护是业务资产，不能为了对标而取消。

## 8. 最小化实施方案

### 8.1 目标与原则

**目标：** 用最小改动，让两条业务各形成一个可验收的闭环：

- A：分享访客（已登录、有可联系依据）→ 一键进入 CRM → 销售在 CRM 看到来源/意向/轨迹 → 记录跟进。
- B：企微存量客户 → 导入 CRM → 补全画像/身份 → 分配/认领 → 跟进。

**原则：**

1. **CRM 是唯一客户主档**；Go 追踪只提供行为事实和意向参考，不维护第二套销售状态。
2. **不双写**：A 线要么走现有 lead outbox，要么走 CRM 新接口，二选一，不能两边都写。
3. **服务端事实**：分享/收藏/咨询/预算完成必须是服务端确认，不能用客户端点击冒充。
4. **幂等**：同一访客/同一 lead/同一 external_userid 重复提交只产生一条客户/一条事件。
5. **权限先于数据**：CRM 读轨迹前重新校验 `can_view`/`can_crm`，不能借 tracking 权限越权看客户。

### 8.2 两条可选路线

#### 路线 A：复用现有 lead outbox（最快，2-4 人日量级）

1. 允许 CRM 开启时，`POST /visitors/:id/lead` 仍创建 `customer_leads`，但把它定位为“来源投递记录”，不是销售状态。
2. 现有 `crm_sources.go` 会把它投递到 `/ingest/miniprogram`；CRM 得到 `pending` 客户，`crm_source.submittedBy = user_id`、`channel = share_tracking`、`summary = 行为摘要`。CRM 客户详情的 `WorkflowDetails` 已经会渲染这段摘要（[customerWorkflow.tsx:51-52](../../background/src/pages/customerWorkflow.tsx#L51-L52)），所以路线 A 不需要新表就能让销售看到“近30天到访 N 次、看了哪些素材”的文字摘要。
3. 新增 `GET /api/v1/management/tracking/by-user/:userId/summary`（或复用 `/visitors/u:<id>`），CRM 客户详情用 `crm_source.submittedBy` 拉取完整轨迹。
4. 解决 409 的 UX：CRM 开启时按钮改为“提交 CRM 候选”，成功后提示“已提交，待客户主管分配”，不再显示死路错误。

**优点：** 改动小，复用 outbox/幂等/重试；不需要新表；销售立刻能看到摘要。  
**缺点：** 证据只有摘要；CRM 客户仍无 owner；旧 lead 状态不会回写；需要约定“lead 是投递记录，不是销售状态”。

#### 路线 B：CRM 原生候选接口（更干净，5-8 人日量级）

1. Go 新增 `POST /api/v1/management/tracking/visitors/:key/crm-candidate`：
   - 校验 `can_crm`、身份门控、去重（同一 `visitor_key` 只建一次）。
   - 调用 Java 内部 `POST /internal/management/v1/tracking/candidates`。
2. Java 新增 `TrackingCandidateController`：
   - 入参：`visitorKey, miniUserId, name, phone, wechat, intentLevel, intentReasons, evidence, shareId, sharerId, channel, occurredAt`。
   - 幂等键：`visitorKey`（唯一索引）。
   - 建 `crm_customer`（`lifecycle=pending`, `addedTimeSource=share_tracking`, `intent` 按传入/未知）。
   - 写 `crm_source(kind=share_tracking, externalId=visitorKey, submittedBy=miniUserId, channel=...)`。
   - 写 `crm_tracking_event`（行为证据时间线）。
   - 归属：`sharerId` 是有效员工则设为 owner；否则 pending + 通知主管。
3. Java 新增 `GET /internal/management/v1/customers/:id/tracking`：
   - 按 `miniUserId`/`visitorKey` 调 Go 只读接口，返回轨迹摘要/会话。
4. React：
   - CRM 客户详情加“小程序轨迹”区块。
   - 分享记录页按钮改为“转入 CRM”；成功后跳 CRM 客户。
   - CRM 增加“行为候选”队列（pending + source=share_tracking）。

**优点：** 语义干净、证据完整、可直接归属、可审计。  
**缺点：** 新表/新接口/新 UI，改动大于 A。

> **建议：** 如果目标是 1-2 周内看到闭环，先做 A；如果目标是长期把 CRM 作为唯一主档，直接做 B，A 只作为过渡。不要把 A 的 lead 状态当成销售状态，否则又会回到“两套状态”。

### 8.3 最小数据模型（路线 B）

```sql
-- 客户身份（统一解析）
CREATE TABLE crm_customer_identity (
  id VARCHAR(36) PRIMARY KEY,
  customerId VARCHAR(128) NOT NULL,
  kind VARCHAR(24) NOT NULL,        -- mini_user / wecom_external / unionid / phone
  valueHash VARCHAR(64) NOT NULL,   -- 不存明文；按需保留掩码
  verifiedAt DATETIME(6),
  source VARCHAR(32),               -- share_tracking / wecom_sync / report / manual
  createdAt DATETIME(6),
  UNIQUE KEY uk_identity (kind, valueHash)
);

-- 行为时间线（CRM 侧只读副本/摘要）
CREATE TABLE crm_tracking_event (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  customerId VARCHAR(128) NOT NULL,
  visitorKey VARCHAR(128) NOT NULL,
  eventType VARCHAR(32) NOT NULL,   -- share_entry/page_view/favorite/consultation/intent_change
  payload JSON,
  occurredAt DATETIME(6),
  createdAt DATETIME(6),
  INDEX idx_tracking_customer (customerId, occurredAt)
);

-- 客户主档补字段（或放 identity 表）
ALTER TABLE crm_customer
  ADD COLUMN trackingVisitorKey VARCHAR(128) NULL,
  ADD COLUMN miniUserId BIGINT NULL,
  ADD COLUMN unionid VARCHAR(128) NULL,
  ADD COLUMN externalUserid VARCHAR(128) NULL,
  ADD COLUMN sourceChannel VARCHAR(64) NULL,
  ADD COLUMN intentLevel VARCHAR(12) NULL;  -- 需同时支持 unknown
```

## 10. 需要业务拍板的 9 个问题

1. **CRM 目标形态**：继续用 phase1 最小 CRM，还是把完整 iyque 接进统一后台？这决定后面是“补接口”还是“换底座”。
2. **分享访客进 CRM 的触发**：只允许“已登录 + 明确身份/留资”，还是允许“匿名候选”进入观察队列？后者需要单独评分，不能叫高意向。
3. **预算页分享的产品口径**：只分享“预算工具”，还是要分享“我这份预算结果”？后者需要服务端快照/公开只读页。
4. **企微加好友是否作为主转化动作**：如果是，需要“分享页 → 带 state 的企微活码 → 回调 → CRM”的桥；如果不是，以留资/咨询为主。
5. **90 天保护期与 90 天原始留存是否匹配乡墅周期**：保护期是业务规则，留存是数据规则，两者要分别批准。
6. **归属规则**：分享人（员工/设计师）是否自动成为 CRM 负责人？现有代码不自动；建议“推荐 + 主管确认”，避免抢单。
7. **匿名访客的意向展示**：是否允许单独“匿名候选”分？如果不允许，就删掉“匿名高意向池”按钮，避免销售空跑。
8. **飞鱼的使用边界**：如果继续投巨量广告，建议飞鱼承接广告线索、API 推送到自建 CRM；不要在自建里重造外呼/广告回传。
9. **CRM 角色是否拆分**：当前 CRM 侧只有 `admin/staff`，客户主管拥有分配、交接、合并、成交/归档审批等全部权限；如果门店/城市负责人需要独立授权，必须拆角色，否则“主管”权限过大。
