第 1–3 步已按本方案实现并通过测试，**未部署**。

| 步骤 | 状态 | 与原方案的差异 |
|---|---|---|
| 1. 邀请码误读场景值 | ✅ | 小程序只认 `query.invite_code` / `query.scene` 且必须是 6 位字母数字，并补上 `onShow`；后端不再把纯数字当 user_id |
| 1. 效果图收藏 | ✅ | `onLike` 改走 `/favorites`（服务端同步收藏数并确认收藏回执）；收藏数改为本地 ±1 |

| 2. 带意向进 CRM | ✅ | 投递载荷加 `intent`；新客户默认意向由"中"改为"待判断"（`unknown`）；后台意向映射加"待判断" |
| 3. unionid | ✅（**偏保守**） | 企微快照读取 unionid，小程序线索带 unionid，存入 `crm_source`（Flyway `V6`）。两边 unionid 一致时**只给主管发"疑似同一客户"通知，不自动合并**，因为《线索移交与跟进入口约定》仍规定系统不自动合并 |

已知限制：
- 用户已有未关闭线索时，再次转化只追加证据，不会刷新 CRM 里的摘要（outbox 只在姓名/电话/微信/摘要变化或有新跟进时重投）；
- 已经投递过的历史线索不会补 unionid 和意向；
- 小程序和企微不在同一开放平台主体下时拿不到 unionid，第 3 步自动失效，不影响其余功能。

上线注意：
1. **先发布 `8e403e9`（第 0 步）**，再发布本分支；
2. 后端会自动执行 Flyway `V6__source_unionid.sql`（给 `crm_source` 加一列和一个索引，可回滚：`DROP INDEX idx_source_unionid; ALTER TABLE crm_source DROP COLUMN unionid;`）；
3. 默认意向变更只影响**新建**客户，已有客户的意向不变；
4. 历史邀请数据**没有**被修改，污染范围需要用文内 SQL 先评估。

验证：Go 全量、phase1 Java 50→52 项、后台 644 项、小程序新增 16 项测试均通过。小程序全量里另有 4 个失败与本分支无关（客服页 2 个在干净 HEAD 上就失败；首页 2 个由工作区里他人未提交的首页改动导致）。本机运行 Go 的 `route` 包测试需要 `CGO_ENABLED=0`（`go-m1cpu` 与本机系统不兼容）。

## 1. 最终结论

| 问题 | 结论 |
|---|---|
| 现有代码能否实现？ | **大部分能。** 分享跟踪（令牌、访客、行为、意向）和企微导入（回调、全量同步、建档）都已经有了。缺的只是**两处"接线"**：分享访客进不了 CRM（CRM 开启后返回 409）；企微客户和小程序用户对不上（不取 unionid）。另有 **3 个 Bug** 要先修。 |
| 分享跟踪是否齐全？ | **采集够用。** 谁分享、谁打开、看了什么、停留多久、有没有咨询，都能回答。最小闭环不需要再加埋点。 |
| CRM 能否承接？ | **能建档和跟进，但收不到意向。** 投递 CRM 时没带意向，CRM 新客户一律默认"中意向"。补一个字段即可。 |
| 对标飞鱼 | 飞鱼是广告线索工具，对接企微要靠第三方集成平台。最小方案**不需要对标**；以后要做分配和去重规则时，可以参考它。 |

## 3. 最小化实施方案（约 4–6 人日）

### 第 0 步：把 `6b38940` 发到生产（不需要开发，发布时间另计）

生产缺的 `8e403e9` 修了线索工作台的四个问题。按该提交的说明，线上审计发现 28 条待处理线索全部没有联系方式，另有 19 条同一人的重复线索：
- 新线索自动补上账号绑定的手机号；
- 超时口径加 48 小时宽限；
- 漏斗按账号去重；
- 修正"未分配"的判断。

第 2 步要把线索送进 CRM，没有手机号的线索进去了顾问也没法联系，所以**这次提交要先上线，或者和第 1 步一起发布**。

注意：上线当天"超时"数会大幅下降，这是统计口径修正，不是数据丢失，需要提前告知运营。

### 第 1 步：修 3 个 Bug（约 1 天）

| # | 问题 | 改法 | 文件 |
|---|---|---|---|
| 1 | 邀请码误读场景值 | 只读 `query.invite_code` 和 `query.scene`，并在 `onShow` 里也处理；后端删除"纯数字视为 user_id"的兼容 | `miniprogram/miniprogram/app.ts`（.ts 和 .js 都改）、`service/model/user_invite_code.go` |
| 2 | 效果图收藏不产生意向证据 | 收藏按钮改调已有的 `favoriteApi`（会走 `ConfirmFavorite`） | `pages/templatesquaredetails/templatesquaredetails.ts` |
| 3 | 效果图手机号按钮没反应 | 参照 `generatedetails.ts` 已有的 `onEnterpriseWechatPhoneAuth`，补上同名方法 | 同上 |

验收：
- 邀请卡片冷启动、热启动都能绑到正确的邀请人；`scene=1007` 不再产生邀请关系；
- 效果图收藏后，访客意向的证据里出现"服务端确认收藏"；
- 手机号授权能走通。

历史邀请数据**先不改**，只用下面的 SQL 评估污染范围，由运营和财务决定是否修正：

```sql
SELECT inviter_user_id, COUNT(*) n FROM invite_relations GROUP BY 1 ORDER BY n DESC LIMIT 20;
```

### 第 2 步：分享访客进 CRM（约 2–3 天）

复用现有的线索投递通道，不新建接口，也不新建表。

1. **去掉 409**：CRM 开启时，"转为销售线索"照常写入 `customer_leads`。这条线索只是一条**投递记录**，线索工作台对它仍然只读，跟进统一在 CRM 里做。（`share_tracking_lead.go:171`）
2. **把意向带过去**：投递时增加 `intent` 字段；CRM 收到后，只在新建的待分配客户上使用它。（`crm_sources.go:61`、`CustomerWorkflow.java` 的 `Ingest`）
3. **默认意向改为"待判断"**：没有传意向时不再默认中意向。（`Models.java:17`，前端意向映射加一个 `unknown`）
4. 销售在 CRM 里看客户的"来源摘要"（现有页面已经会展示）：里面有访问次数、看过的素材和意向理由，暂时不做完整轨迹页。

验收：
- 在"分享访问记录"里点"转为销售线索"，5 分钟内 CRM 出现一个待分配客户，带意向和行为摘要；
- 重复点击不会产生第二个客户。

### 第 3 步：企微客户和小程序用户对上（约 1.5–2 天）

1. phase1 拉企微客户详情时，多读一个 `unionid`，存到来源记录上。（`WecomGateway.java`、`ImportService.java`，加一个 Flyway 迁移，给 `crm_source` 增加 `unionid` 列和索引）
2. 投递小程序线索时带上用户的 `unionid`（`users` 表已有这个字段）。
3. CRM 收到时按 unionid 查：
   - 命中的客户**没有受保护的归属** → 把这条来源挂到同一个客户下；
   - 命中的客户**已有受保护的归属** → 只给主管发"疑似同一客户"通知，不自动合并（遵守仍在生效的《线索移交与跟进入口约定》：系统不自动合并小程序线索与企微客户档案）。

前提：小程序和企业主体绑定在同一个微信开放平台下（`reportwecom` 已经依赖这个前提），否则拿不到 unionid，这一步会自动失效，也不影响其他功能。

验收：
- 同一个人先在小程序咨询、后加企微，CRM 里只有一份档案、两条来源。

## 4. 明确不做（后置）

这些都有价值，但不是跑通闭环所必需的：

- 新建 CRM 候选接口、身份表、行为时间线表，以及 CRM 详情里的完整轨迹页；
- 匿名访客的候选评分；放宽意向门槛；预算测算完成事件；
- 移植源雀的活码、标签、欢迎语、Excel 线索池；
- 自动分配规则、按飞鱼思路做的去重和回收规则；
- 延长令牌 30 天、数据保留 90 天的期限；
- 外呼、广告回传、会话存档；
- 预算结果页快照（不是闭环的必要条件）。

以后跑通、有了真实数据，再按需求逐项加。
