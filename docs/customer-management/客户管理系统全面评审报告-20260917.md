| 维度 | 结论 | 评价 |

## 二、三层权限模型与校验链路

### 2.1 权限模型

| 层级 | 载体 | 取值 | 职责 |
| --- | --- | --- | --- |
| 第一层：平台访问范围 | Go `management_access.scope` | `platform_admin` / `crm_only` | 控制能进入后台哪些模块 |
| 第二层：客户数据角色 | Java `account.role` | `admin`（主管）/ `staff`（顾问） | 控制客户数据的可见与操作范围 |
| 第三层：企微员工绑定 | `management_wecom_identity` + `employeeId` | 具体员工 | 决定顾问能看到"谁的客户" |

三层独立授权、逐层收窄；账号可只有平台管理员身份而无客户角色（`crmContext` 为空），也可只是顾问且仅见本人客户。

### 2.2 校验链路（纵深防御）

```
前端菜单过滤（sidebar）→ 前端路由守卫（ProtectedRoute）→ 页内 tab 白名单
  → Go：AuthRequired + ManagementAccessRequired（crm_only 服务端白名单：/me、/logout、/crm/*）
  → Go→Java：HMAC-SHA256 签名 + nonce 防重放 + ±60s 时间窗 + 路径白名单
  → Java：ManagementBridgeFilter 验 managed 账号/员工在职 → 服务层数据过滤（查询层强制）
```

亮点：

- 数据范围过滤下沉到查询层（CustomerService specification），列表、导出、附件、工作台同一口径；
- 企微会话与授权版本号（`wecom_version`）绑定，解绑/换绑/停用授权后旧会话下一次请求即失效；
- 关键操作双审计（`crm_operation_audit`、`management_access_audit`）；
- 自保护：不能停用或降级当前操作者自身。

## 三、分维度分析

### 3.1 权限体系

三类角色权限矩阵（摘要）：

| 能力 | platform_admin | 客户主管 admin | 顾问 staff | 合理性 |
| --- | --- | --- | --- | --- |
| 后台全部模块 | 是 | 否 | 否 | 合理，平台运维与客户业务分离 |
| 查看全量客户 | 是（有客户角色时） | 是 | 仅自己名下 + 公海 | 合理 |
| 调整负责人 / 交接 / 释放公海 | 是 | 是 | 否（403） | 合理 |
| 审批（成交/归档/争议/合并等） | 是 | 是 | 仅可提交申请 | 合理，顾问发起、主管裁决 |
| 公海认领 | 是 | 是 | 是 | 合理 |
| 企微同步 / 账号列表 / 工作台 | 是 | 是 | 否 | 合理 |
| 授权管理（开通客户权限） | 是 | 否 | 否 | 合理，人事级授权归平台管理员 |

**结论：符合最小权限原则，主管与顾问边界（审批、归属调整、团队数据）划分干净。**

发现的问题见第四节（P1-2、P2-2 等）。

### 3.2 登录流程

企微登录（`service/route/wecom_identity.go`）：

```
点击"企业微信登录"→ /wecom/start
  → state + browser 双随机值（只存 SHA256），Path 限定 cookie（5 分钟）
  → UA 分流：企微内 snsapi_base 静默授权；PC 浏览器 qrConnect 扫码
  → 回调：一次性 DELETE 校验 state/browser/corp/agent 四项匹配
  → 查绑定：identity.enabled + user_type='management' + access.enabled + scope 合法
  → 写会话（auth_method=wecom、wecom_version、8 小时）→ 直达 /admin/customer-management
  → 后续每次请求 checkWecomSession 复核绑定与版本
```

账号密码登录：仅 `user_type='management'`；Go 侧按账号限流 20 次/5 分钟；Java 独立登录按 IP 限流 15 次/15 分钟；bcrypt(12)；会话 Redis 存储、8 小时、Secure/HttpOnly/SameSite=Lax；非开发环境 `SESSION_SECRET < 32` 字符拒绝启动。

问题见第四节（P0-1、P0-2、P1-1）。

### 3.3 业务逻辑

生命周期闭环：

```
企微添加 / 小程序咨询 / 手动报备 → 建档（pending 待完善 / legacy 历史待核实）
  → 归属保护 90 天（有效跟进/沟通/出图/报价续期）→ 到期自动入公海（分批释放）
  → 任一扫认领（version 乐观锁）→ 重新获得保护 → 主管交接 / 释放
```

审批流覆盖：成交确认（需附件）、无效归档、归属争议、共用电话独立报备、重复档案核实/合并。

一致性保障：version 乐观锁、企微快照不覆盖人工资料、历史纳管一次性（`historicalReviewed`）、时钟水位防旧事件覆盖、导出公式转义与上限 2 万条。

问题见第四节（P1-3、P1-4）。

### 3.4 页面跳转

| 守卫 | 位置 | 行为 |
| --- | --- | --- |
| 路由守卫 | `background/src/component/ProtectedRoute.tsx` | 未登录 → /login；crm_only 访问非客户管理路径 → 强制重定向（fail-closed 写法正确） |
| 菜单过滤 | `background/src/component/sidebar.tsx` | crm_only 仅显示"客户管理"；未开通 CRM 不显示该项 |
| 页内 tab 白名单 | `background/src/pages/customerManagement.tsx` | 主管才见"工作台/同步"，平台管理员才见"线索/授权"；越权 tab 回落合法 tab |

跳转链评价：企微登录直达正确；401 事件清理会话回登录页正确；密码登录多一跳（P1-1）；tab 直达越权时地址栏不校正（P2-1）。

## 四、问题清单与主项意见

### P0-1 Java 独立登录（standalone）默认开启

- 现象：`crm.standalone-enabled` 默认 `true`（`application.yml`），生产靠环境变量显式关闭；漏配即暴露第二个独立登录入口与旧 /api 管理接口。
- 影响：安全配置依赖人工，默认值方向不安全。
- **主项意见：采纳，本期实施。** 默认值改为 `false`（fail-closed），演示容器显式开启；测试同步更新，新增"默认关闭时 /api 入口整体 403"断言。
- 安排：迭代 A（A1）。

### P0-2 企微离职后的会话窗口（最长 8 小时）

- 现象：通讯录停用不会立即失效已有会话；`wecom_version` 不含通讯录在职状态，`checkWecomSession` 无法感知离职。
- 影响：离职员工最长 8 小时仍可访问客户数据。
- **主项意见：分两层处理。** ①即时生效路径已存在——停用后台授权（`management_access.enabled`）后下一请求即 401，因此"离职当天停用后台授权"作为强制运维流程立即执行；②技术收敛（周期性复核企微员工在职状态，将窗口压到分钟级）涉及跨服务调用与失败策略设计（服务不可用时是否放行），列为下期设计评审后实施。
- 安排：运维项 O1（立即）；迭代 B（B2，设计评审后实施）。

### P1-1 密码登录后跳转多一跳

- 现象：`login.tsx` 固定 `navigate('/dashboard')`，crm_only 账号随后被 ProtectedRoute 二次重定向到 /customer-management，出现白屏闪跳。
- **主项意见：采纳，本期实施。** Go `/login` 响应补充 `scope` 与 `crmEnabled`（前端类型已预留），前端按 scope 直达。
- 安排：迭代 A（A2）。

### P1-2 前端 platform 判定 fail-open

- 现象：`customerManagement.tsx` 中 `platform = scope !== 'crm_only'`；scope 缺失或未来新增枚举值时会被当作平台管理员（服务端 403 兜底，无实际越权）。
- **主项意见：采纳，本期实施。** 改为显式 `=== 'platform_admin'`（fail-closed）。
- 安排：迭代 A（A3）。

### P1-3 编辑表单负责人下拉与 409 文案

- 现象核查（本次修正原结论）：该下拉仅对无客户编号的"历史待核实（legacy）"客户渲染，与后端"仅 legacy 可直接改归属"恰好配对，不是死代码；但其只写 `ownerId`（员工号）不写 `ownerUsername`（账号），单独使用会让"历史纳管"卡在"请先确认归属账号"，与「分配/交接」（同时写两字段）构成双入口。非 legacy 场景的 409 文案"报备客户在保护期内锁定归属"对企微/成交客户不准确。
- **主项意见：采纳但修正方案。** 删除编辑表单负责人下拉，归属调整统一走「分配 / 交接」单入口；Java 409 文案改为引导语。
- 安排：迭代 A（A4）。

### P1-4 授权失败卡单无自动补偿（C05）

- 现象：授权两阶段流程失败后（远端开通失败或进程中断），本地保持禁用（安全方向正确）；`pending` 态在异常中断时无自动恢复，需人工重新保存。
- **主项意见：采纳，下期实施。** 需要"卡单检测 + 主管可见的重试入口 + 幂等重放"设计（意图可从审计 `after_value` 重建），本期保留现有手动重试路径（刷新后重新保存即重试）。
- 安排：迭代 B（B1）。

### P2-1 越权 tab 直达时 URL 不校正

- 现象：`?tab=` 无权限时静默回落合法 tab，但地址栏仍显示原参数。
- **主项意见：采纳，本期实施（小修）。** 回落后以 `replace` 校正 URL。
- 安排：迭代 A（A5）。

### P2-2 平台管理员互停无二次确认

- 现象：自保护只保证操作者不停用自己；两个管理员可互停，极端场景可能停掉最后一个可用管理员。
- **主项意见：采纳，本期实施。** 对"平台管理员被停用或降级"增加二次确认（沿用项目既有 `window.confirm` 交互模式）。
- 安排：迭代 A（A6）。

### P2-3 登录限流为进程内存态

- 现象：Go 与 Java 限流均按进程内存储，多实例部署失效。
- **主项意见：维持现状（条件触发）。** 当前单机部署有效；多实例部署前升级为集中式（Redis）。列入迭代 B（B3）。

### P2-4 双请求层 401 策略未统一

- 现状：Go 会话层与 Java 独立会话层的 401 处理策略差异（已在 0916 评审记录）。managed 模式下属低频路径。
- **主项意见：维持现状，列入迭代 B（B4）待排期。**

### 已接受项（维持现状，记录在案）

- 记住密码明文 localStorage：用户已书面确认方案 B；边界为仅本机使用，不共享设备。
- 授权两阶段失败保持禁用（安全方向正确）：人工重试路径已存在，自动补偿见 B1。
