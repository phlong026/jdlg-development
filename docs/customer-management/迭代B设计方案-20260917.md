## 二、B1 授权补偿设计

### 2.1 目标与不变量

- 目标：授权两阶段流程在"远端失败/进程中断/服务不可用"后，具备 **卡单检测 → 平台管理员一键重试 → 幂等重放 → 定时自动补偿** 的闭环；安全方向不变（失败保持禁用）。
- 不变量（保持现状）：
  - 远端未确认成功前，`management_crm_link.enabled` 恒为 FALSE（先禁用后开通）；
  - 终局写入以 `management_access.version==revision` 乐观锁串行化，用户新操作永远覆盖重放；
  - 审计只记录**真实发生的结果**（active/failed），不写"意图"。

### 2.2 数据模型变更

新增迁移文件 `service/sql/management_crm_link_intent_up.sql`（对齐 `*_up.sql` 先例，发布顺序：先应用 SQL，再发布 Go 服务）：

```sql
ALTER TABLE management_crm_link
  ADD COLUMN intent TEXT NULL COMMENT '待执行授权意图（JSON），终局成功后清空',
  ADD COLUMN attempts INT NOT NULL DEFAULT 0 COMMENT '自动重放已尝试次数';
```

- `intent` 仅由准备事务写入、终局事务成功后清空；内容为完整意图：
  `{userId,revision,scope,enabled,displayName,employeeId,role,crmEnabled,operatorId}`
- 服务对未迁移环境的降级：读 `intent` 报 1054（unknown column）时，重试端点返回 503"补偿结构未就绪"，自动补偿 worker 记一次日志并跳过——不影响现有授权功能。

### 2.3 Go 服务端改造

1. **准备事务**（crm_access.go 现有 L162–168）：
   - `management_crm_link` 的 UPSERT 增加 `intent=VALUES(intent), attempts=0`，写入上述 JSON（`operatorId=GetUserID(c)`）。
2. **终局事务**（现有 L182–209）：成功分支增加 `intent=NULL`。
3. **新增 `POST /access/retry`**（platform_admin + `crmMutationAllowed`，body `{userId}`）：
   - 锁定读取 `SELECT version,state,intent,attempts FROM management_crm_link WHERE user_id=? FOR UPDATE`；`state!='pending'` 或 `intent` 为空 → 409"该账号没有待重试的配置"；
   - `revision=link.version`，按 intent 重放 `POST /provision/accounts`（`enabled=crmEnabled&&enabled`）；
   - 成功 → 终局事务：检查 `management_access.version==revision` → 置 `state='active',enabled=TRUE,intent=NULL`，按 intent 更新 `management_access.scope/enabled`，写审计（`action='save_access'`，operator=当前管理员）；若版本已被新操作越过 → 409"授权已被新操作更新，请刷新查看"；
   - 失败 → 保持 pending，`attempts+1`，写审计 result='failed'（intent 保留），返回 502 附原因；Java 明确 409（版本冲突）时同时说明"请刷新后核对最新状态"。
4. **自动补偿 worker**（新文件 `service/route/crm_access_compensate.go`，启动模式参照 `VirtualPayCompensator.loop()`/`wecomEventInbox` 的 goroutine）：
   - 每 60 秒扫描：`state='pending' AND intent IS NOT NULL AND attempts<5 AND updated_at<NOW(6)-INTERVAL 60 SECOND LIMIT 5`；
   - 抢占式计数：`UPDATE management_crm_link SET attempts=attempts+1,updated_at=NOW(6) WHERE user_id=? AND version=? AND state='pending'`，受影响行=1 才继续（防止与手动重试并发重复执行）；
   - 重放成功 → 终局事务同上（审计 `operator_id=0` 表示系统重放，after_value 附 `"replay":true`）；失败 → 保持 pending 等待下一轮；
   - `attempts>=5` 后停止自动重放（保留手动重试入口），日志告警提醒人工介入。

### 2.4 Java 幂等契约（ManagementProvisionController.save）

将版本判断拆为三段（其余逻辑不变）：

```java
if(i.revision<1) throw new ApiException(409,"授权版本无效");
if(a!=null && i.revision<a.getManagedRevision()) throw new ApiException(409,"授权版本已过期");
if(a!=null && i.revision==a.getManagedRevision()) {
  // 重放到达时首次调用已成功：参数一致则幂等返回，不做任何副作用（不删会话、不改动）
  boolean same = Objects.equals(a.getManagementUserId(),i.userId())
      && Objects.equals(a.getDisplayName(),i.displayName())
      && Objects.equals(blankToNull(a.getEmployeeId()),blankToNull(i.employeeId()))
      && Objects.equals(a.getRole(),i.role())
      && a.isEnabled()==i.enabled();
  if(!same) throw new ApiException(409,"授权版本已过期");
  return a;
}
```

要求：`blankToNull` 与首次保存的归一化一致（blank→null）；幂等分支不执行 `sessions.deleteByUsername`。

### 2.5 前端（AccessPanel）

- 列表行：`state==='pending'` 的行文案改为"待处理（配置未完成）"；
- 保存失败：**保留** `selection`（不再 `setSelection(null)`），提示"配置未完成，可重试或修改后重新保存"；
- 选中 pending 行时，表单下方显示「重试未完成的配置」按钮 → `POST /access/retry {userId}`；成功后 `message='配置已完成'` 并 `reload()`；
- 失败（502/409）时展示服务端原因，保持表单可编辑。

### 2.6 验收标准

1. 模拟 Java 服务不可用：保存授权 → 502、行保持 pending（intent 落库）、`management_access` 版本 +1；
2. 恢复 Java → 60 秒内自动补偿转 active，审计出现 `operator_id=0` 的重放记录；或平台管理员点击重试立即转 active；
3. 崩溃注入（远端成功后、终局前杀进程）：重启后补偿重放，Java 幂等返回，终局转 active，不产生重复账号/副作用；
4. 重放期间用户另行保存：用户操作胜出（版本 +1），重放因乐观锁/Java 版本判断退出，无脏写；
5. `attempts>=5` 后自动重放停止，手动重试仍可用；
6. 未应用迁移的环境：现有授权流程不受影响，重试端点返回 503 提示。

## 三、B2 企微在职复核设计

### 3.1 目标

将离职（通讯录停用/删除/移出应用可见范围）后的**会话失效窗口从小时级压缩到分钟级**，且同时覆盖 CRM 数据与 Go 平台功能；不改变任何已有防线。

### 3.2 复核点

在 `wecom_identity.go checkWecomSession`（绑定校验通过后）追加在职复核：

```
绑定表校验通过 → wecomRosterCache.ensureActive(cfg, employeeId)
  ├─ 在职 → 放行
  ├─ 明确离职（errcode=46004 用户不存在 / user/get status!=1）→ 401"企微员工已停用，登录已失效，请重新登录"
  └─ 调用失败（网络/权限/其他 errcode）→ 降级（见 3.4）
```

- 复用 `wecomIdentityProvider.member()`（内部走 `authorizedCall` + token 缓存 + 40014/42001 刷新），provider 实例由 `registerWecomLogin` 持有并在包级共享给复核路径；
- 复核仅对 `auth_method=wecom` 会话生效（与绑定机制一致）；账号密码登录的 managed 账号由 Java roster 兜底（30 分钟），差异在文档记录。

### 3.3 缓存与频率

- 新增包级 `wecomRosterCache`（`sync.Mutex + map[corp+employeeId]entry`，entry 含 `active/until`）：
  - 新鲜命中（`now<until`）直接判定，不发起外部调用；
  - 过期后调用 `user/get`：TTL=5 分钟（在职/明确离职均缓存 5 分钟）；
- 外部调用频率上限：每员工每实例 ≤ 1 次/5 分钟；多实例下每实例一份缓存（可接受，后续可并入 B3 的 Redis 通道）；
- 员工改绑/解绑已由绑定表 version 机制即时失效，缓存不构成绕过。

### 3.4 降级策略（评审决策点）

| 场景 | 行为 | 理由 |
| --- | --- | --- |
| 企微 API 调用失败，缓存有旧值 | 沿用旧值（stale）放行，`until=now+60s`，记日志 | 避免企微抖动造成全员误踢 |
| 企微 API 调用失败，无缓存 | **放行**（fail-open），`until=now+60s`，记日志 | 复核是新增防线，原有防线（绑定表、8 小时窗口、Java roster）不变；fail-closed 会把可用性风险引入登录主链路 |
| 明确离职响应 | 拒绝并 401 | 精确判定，不受降级影响 |

### 3.5 边界与不做项

- 企微**通讯录变更事件回调**（事件驱动即时失效）复杂度高（独立回调加解密、企微后台配置），列为长期方案，本期不做；
- 运维项 O1（离职当天停用后台授权，下一请求即 401）继续保留为即时路径，B2 是其技术补充而非替代；
- `management_wecom_identity` 是登录绑定（登录主体），本设计不自动解绑离职员工（保留人工处置）。

### 3.6 验收标准

1. 通讯录停用员工 A、且其已有 wecom 会话：≤5 分钟 + 一次请求内，A 的任意管理请求返回 401 并清会话；
2. 停用后重新启用：恢复访问（缓存 TTL 内最多滞后 5 分钟）；
3. 模拟企微 API 故障（错误凭据）：在职员工不受影响（降级放行），日志有降级记录；恢复后复核重新生效；
4. 绑定表停用/改绑路径不受缓存影响（原即时失效保持）。

## 四、B4 失效语义与 401 统一设计

### 4.1 前端双请求层统一（B4a，先行）

- 新增统一入口 `background/src/utils/session.ts`（或并入现有 tokenUtils）：

```ts
export function expireSession() {
  tokenUtils.removeToken();
  window.dispatchEvent(new Event('management-session-expired'));
}
```

- `utils/request.ts` 401 分支：删除 `window.location.href='/admin/login'` 硬跳，改为 `expireSession()`；
- `api/wecomCustomers.ts crm()` 401 分支：改为 `expireSession()` + 抛 CRMError（提示文案不变）；
- 跳转由既有链路完成：事件 → `ManagementSession` 清空 user → `ProtectedRoute` `<Navigate to="/login" replace/>`（全部受保护页面均已包裹，结构条件已核实具备）；
- 效果：两请求层 401 行为完全一致（同一函数、同一事件、同一软跳），消除硬跳导致的整页刷新与状态丢失。

### 4.2 Go↔Java 失效语义映射（B4b）

1. **Java**：`ManagementBridgeFilter.reject()` 增加 `code` 字段（JSON 保持向后兼容）：
   - "客户账号未关联或已停用" → `"account_inactive"`；
   - "员工已停用" → `"employee_inactive"`；其余响应不带 code；
2. **Go `crmProxy`**：非 2xx 分支解析 `code`；命中 `employee_inactive`/`account_inactive` 时 `ClearUserSession(c)` 并返回 401"<原消息>，请重新登录"，前端 crm() 走 4.1 统一登出；
3. 保留区分（设计取舍）：
   - Java 桥接 401（nonce 重放/时间戳过期/签名错误）是**服务对接问题**而非用户会话失效，维持 Go→502 + 服务端日志，不误导用户为"登录失效"；
   - Go 侧 403"尚未关联可用的客户管理账号/此账号仅可访问客户管理模块"是**功能禁用/范围限制**，非会话失效，维持 403 透传。

### 4.3 边界与不做项

- standalone 独立会话层（Java `AuthService` 的 401/403）在 A1 后默认关闭，本期仅文档记录其语义，不做改造；若未来 standalone 常开，再并入本设计；
- 企微登录 401 文案（"企微身份绑定已变更或登录已过期"）已走统一通道，无需改动。

### 4.4 验收标准

1. 登录过期后，在 dashboard/users/oss 等任意页面触发请求 → 软跳登录页，无整页刷新、无白屏闪跳；
2. Java 侧将某员工置为停用（模拟 roster 生效）→ 该员工下一个 CRM 请求收到"员工已停用，请重新登录"，前端统一登出；
3. 桥接签名错误（构造坏 nonce）→ 用户看到 502"客户服务连接失败"，不被登出。

## 五、B3 限流集中化设计

触发条件：**多实例部署前必须完成**；单机部署下维持现状即可（本期不阻塞上线）。

1. 新增 `service/component/rate_limit.go`：

```go
type RateLimiter interface { Allow(key string, limit int, window time.Duration) bool }
// Redis 实现：INCR + 首次 EXPIRE（固定窗口）；Redis 错误 → 回退内存实现并记日志
// 内存实现：现有 managementLoginGate / crmExportLimiter 的语义原样收编
```

2. 接入改造（语义不变）：
   - `managementLoginGate`：key `mgmt:login:{sha256(lower(account))}`，20 次/5 分钟（大小写归一化保持）；
   - `crmExportLimiter`：key `crm:export:{userID}`，SET NX EX 15（存在即拒绝，等价现语义）；
   - Redis 不可用降级：回退进程内实现（fail-open 方向：限流是防爆破兜底，不应因 Redis 故障阻断登录），启动与回退各记一次日志。
3. 不做项（记录）：
   - Java `AuthService.attempts`（standalone 专用）：standalone 默认关闭后优先级最低，暂不迁移；
   - `crm_sources.go` 来源同步 worker 的进程内 TryLock：仅多实例下任务重复执行，纳入"多实例部署检查清单"（改 DB 行锁或分布式锁），随 B3 排期；
   - 测试可用 miniredis（既有先例 `user_redis_test.go`）。

4. 验收标准：多实例（本地起两个进程）下账号限流与导出门限全局生效；Redis 停机时回退内存限流、登录与导出不中断。

## 七、风险与决策点（评审已确认，2026-09-17）

| # | 决策点 | 建议 | 备选 |
