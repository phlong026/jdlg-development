# 销售线索业务排查与主流 CRM 对标分析

日期：2026-10-17
范围：管理后台「销售线索」（客户 · 线索 · 商机）、「分享访问记录」、「客户管理工作台」，以及背后的 Go 服务（`service/`）、Java 客户服务（`customer-management/phase1`）和小程序入口（`miniprogram/`）。
方式：只读代码排查，没有改代码，也没有连接真实数据库或真实企微环境。下文结论都基于当前快照的代码行为，每条都附了代码位置，方便复核。

---

## 0. 结论先行

1. **系统里有三套“客户”数据、五套状态，彼此不通。** 分享访问记录（访客）、客服线索（`customer_leads`）、客户档案（Java CRM）各管一段。同一个人可能在三处各有一条记录，而且“意向”有三套算法。销售要在三个入口之间来回切，才能拼出一个人的全貌。
2. **设计初心的主链路“内容分享 → 查看记录与意向 → 线索”目前是断的**，有 6 个断点（第 1.2 节）：
   - 预算卡片分享出去后，对方打开的是空白测算页，不是这份预算；
   - 预算结果页不在采集范围内；
   - 只看不收藏、不咨询的人，意向永远停在“低关注”；
   - 匿名访客不能转成线索；
   - 分享人不会成为线索负责人；
   - 启用统一客户档案（CRM）后，“转为销售线索”接口直接返回 409，这条路实际被关掉了。
3. **“线索”和“客户”的边界混乱。** 启用 CRM 后，所有小程序线索（包括已标无效的）每分钟自动同步成“客户档案”里的客户，企微加好友也直接成为客户，等于“任何人都是客户”。没启用 CRM 时，旧线索页又把“已成交”当成线索的终态，中间没有“客户”这一步。
4. **对标主流 CRM，建议采用“线索 = 待验证的信号；客户 = 确认有真实建房需求、能联系上、有负责人的对象；成交 = 客户的一个阶段”。** 好消息是 Java CRM 已经有这道门槛：`待完善报备 (pending)` 补齐 5 项资料并确认归属后，才进入 `专属保护 (protected)`。问题只在于这道门槛被叫作“待完善报备”、放在“客户档案”里，用户看不出来。改造成本可控。
5. **“偏开发视角”的根源**：页面围绕数据口径和技术约束组织，没有围绕“销售今天该联系谁、说什么”组织。页头和正文写满统计口径、快照、规则重算、会话号、任务号；高频入口「线索」在 CRM 模式下却是只读页。

### 1.1 系统地图

- **模式 A，未接 CRM**：线索在客服线索工作台跟进，没有客户档案。
- **模式 B，已接 CRM，即计划的上线形态**：旧线索工作台只读，所有线索同步成 CRM 客户。

### 1.2 入口一：内容分享 → 访问记录 → 线索（设计初心）

| 步骤 | 设计初心 | 代码实际行为 | 位置 |
| --- | --- | --- | --- |
| ① 分享预算卡片 | 用户把分析出的预算卡片发到朋友圈或群 | 分享路径是 `/pages/aicost/aicost?source=cost-share`，对方打开的是**空白测算表单**，不是分享人的这份预算 | `miniprogram/.../aicostresult/aicostresult.ts:127` |
| ② 记录查看 | 记录谁看了这张卡片、看了多久 | 预算结果页 `aicostresult` 在采集策略里是 `excluded / Public:false`，只记得到“访问了造价测算页”，记不到“看了哪份预算”。能按“素材”追踪的，只有后台「创建素材分享」发布的图文和视频 | `service/tracking/routes.json:134` |
| ③ 意向度 | 看得越多、越久，意向越高 | 默认规则 followup-v1：**中** = 已登录 + ≥2 次会话 + ≥1 次收藏成功；**高** = ≥1 次服务端确认的主动咨询提交；**停留时长不单独升级标签**。只浏览不收藏的人永远是“低关注”；而被判成“高”的人已经在智能客服提交过咨询，本来就有线索。所以意向度对发现新线索几乎没有增量 | `docs/share-tracking/intent-rules.md`「已确定范围」 |

| ⑥ CRM 模式 | — | 启用 CRM 后，转化接口返回 **409「客户已统一纳管，请在客户档案中跟进」**，自动转化也随之停用。只剩「查看客户 / 线索」按钮，而且只在该访客已有经核实的 CRM 映射时才出现。**按计划的上线形态，这条链路实际不存在** | `service/route/share_tracking_lead.go:172`、`share_tracking_lead_auto.go:99`、`shareTracking/crmTarget.tsx:13` |

另外，小程序采集开关和同意开关默认关闭（`miniprogram/miniprogram/utils/tracking/index.ts:1`），上线时需要单独开启。

### 1.3 入口二：企业微信客户

- 企微加好友时，经回调或同步进入 Java，新建一条客户：名称“待同步客户”，`lifecycle=pending`，`stage=new`，负责人是添加好友的员工（`ImportService.java:34`）。
- 这条客户出现在「客户档案」和「待完善报备」队列。补齐 5 项资料（姓名/微信、电话、镇村地址、面积与需求、预计建房时间）并确认归属后，进入「专属保护」90 天。
- 企微不返回手机号，所以小程序和企微里的同一个人**不会自动关联**，只能靠主管人工“关联同一客户”（`docs/customer-management/线索移交与跟进入口约定.md` 第 2 节）。
- 企微好友和访问记录之间也没有桥：员工用企微发给客户的小程序卡片，如果客户没登录小程序，打开后仍然是匿名访客。

### 1.4 入口三：客户主动留资 / 员工手动报备

- 智能客服页有 3 个动作会写线索（`customerservice.ts:495 / 757 / 789`）：
  1. 填写结构化需求：**静默**写入；
  2. 点击“一键生成方案”：**静默**写入；
  3. 转人工：显式的咨询请求，走 `/consultation-requests`。
  前两个动作里用户并没有表达“希望有人联系我”，却都成了线索。意向靠关键词打分：留了联系方式 +35，出现“造价/预算”+25，大于等于 60 分为高（`service/model/customer_service.go:386`）。
- **造价测算、方案详情、报告问卷这些强意向工具页本身不产生线索**，只提供打开企微客服的入口。
- 手动报备：顾问在 CRM「新增客户报备」里填 5 项，直接成为受保护客户，跳过线索阶段。

### 1.5 一条记录的完整流转

```
模式 A（未接 CRM）
  访客 ──(手动/自动转，仅限已登录的乡墅业主)──┐
  智能客服留资（含静默草稿、点生成）─────────┴─▶ 客服线索[新线索] ─▶ [已联系] ─▶ [已成交] / [无效]
  企微好友：不进入线索            手动报备：不可用

模式 B（已接 CRM，计划的上线形态）
  访客 ──✕ 409
  智能客服留资 ─▶ 客服线索（只读）─每分钟同步，所有状态，包括无效─▶ CRM[待完善报备]
  企微新好友 ────────────────────────────────────────────────▶ CRM[待完善报备]
  手动报备 ──────────────────────────────────────────────────▶ CRM[专属保护]
  CRM[待完善报备] ─补齐5项+确认归属─▶ [专属保护 90天] ─有效跟进─▶ 续期
                                         └─到期无有效跟进─▶ [客户公海] ─认领─▶ [专属保护]
  成交：顾问提交“成交确认”+凭证 ─▶ 主管确认 ─▶ [成交已确认]
```

同步不按状态过滤，SQL 见 `service/route/crm_sources.go:26`。CRM 侧建档见 `CustomerWorkflow.java:49`。

### 1.6 状态与用词冲突

| 词 | 出现位置与含义 | 冲突点 |
| --- | --- | --- |
| 客户 | ① 访问记录「客户视角」= 访客，含匿名；② 线索详情「客户信息」= 线索；③ CRM 客户档案 = 含待完善的所有人 | 一个词指三种对象 |
| 已成交 | ① 线索状态 `converted`；② CRM 阶段 `won`；③ CRM 生命周期“成交已确认” | 线索可以不经客户直接“成交”；CRM 里阶段和生命周期各有一个“成交” |
| 跟进中 | 线索概览环图把 `contacted` 显示为“跟进中”，列表里同一个状态叫“已联系”；CRM 里另有 `following` | 同一状态两个名字 |
| 意向 | ① 访问记录：规则版本 + 人工修正；② 线索：关键词打分；③ CRM：人工选高/中/低 | 三套口径，用户无法理解“为什么看了 10 次还是低关注” |
| 线索 | 导航「线索」卡片 = 旧客服线索表；CRM 的“待完善报备”实际也是线索 | 真正可操作的线索藏在客户档案里 |

## 2. 与主流 CRM 对标

### 2.1 主流的几种做法（概括常见实践）

- **B2B / 大单型（Salesforce、纷享销客、销售易一类）**：线索（Lead）是未验证的信号，进入线索池，经过分配、跟进、判定（合格 / 不合格）。合格后执行“线索转换”，生成客户 + 联系人（可选同时生成商机）。成交 = 商机赢单，或客户状态变为“成交客户”。**客户 ≠ 成交。**
- **营销自动化型（HubSpot 一类）**：一个联系人只有一条记录，按生命周期阶段推进：订阅者 → 线索 → MQL → SQL → 商机 → Customer。这里的 **Customer = 已成交付费**。
- **企微 SCRM（尘锋、微伴、探马、句子互动一类）**：企微好友在企微术语里就叫“客户”。核心能力是“素材雷达”：员工从企微侧边栏发素材，客户点开后实时提醒这名员工，浏览次数和时长记进客户动态和意向分；客户阶段由销售推进。**归属天然就是发素材的员工。**

这几类的共同点：

1. 线索和客户要么分开存，要么分阶段管理，转化有一个明确的“判定”动作；
2. 行为数据（浏览、停留、转发）作为评分和动态挂在人身上，而不是另起一套“访客系统”让销售去翻；
3. 素材带分享人归属；
4. 有线索池 / 公海、分配规则和超时回收；
5. 一个人一条主记录。

### 2.2 回答：线索和客户怎么定义

**建议采用 B2B 派：线索 = 信号，需要跟进确认；客户 = 确认有意向的对象；成交 = 客户的一个阶段。** 不建议采用“成交才算客户”。理由：

- 农村建房决策周期长（几个月到一两年），成交前需要长期占有和保护。90 天保护期、公海、认领这些规则本来就挂在“已确认的客户”上；如果成交才算客户，这些规则就要挂到线索上，概念会倒过来。
- 企微好友数量大、质量参差（同行、施工队、看热闹的都有），全部直接当客户，会把客户数和转化率口径搞乱。
- HubSpot 的“Customer = 成交”适合低客单、营销自动化驱动的场景，不适合我们“顾问一对一长期跟进”的模式。

**建议的判定标准（线索 → 客户）**，三条同时满足：

1. 能联系上（电话或企微）；
2. 确认是业主本人或家属的真实建房需求（排除设计师、施工队、建材商等 B 端身份）；
3. 有明确负责人。

这在现有 CRM 规则里就是“补齐 5 项资料 + 确认归属”，可以直接复用，不需要再造一套。成交保留现有的“主管核实凭证确认”。

### 2.3 差异表

| 维度 | 主流做法 | 我们现状 |
| --- | --- | --- |
| 记录主体 | 一人一条主记录 | 访客、线索、客户三处各一条 |
| 线索 → 客户 | 显式“转为客户”，有判定标准 | 没有这个动作：旧线索直接“已成交”；CRM 里“待完善报备”本身就算客户 |
| 行为数据 | 挂在线索 / 客户时间线上，参与评分 | 在单独的「分享访问记录」页，要按访客去翻；停留时长不计分 |
| 素材归属 | 谁发的谁跟 | 分享人不带入负责人 |
| 匿名访客 | 引导授权或留资后识别，并合并历史轨迹 | 只观察，不能转 |
| 分配 | 线索池 + 自动分配 + 超时回收 | 线索负责人是手填文本；公海只在 CRM 客户层 |
| 状态数量 | 线索 3–4 个 + 客户阶段 4–6 个 | 5 套状态，近 20 个取值 |
| 意向 | 一个可解释的分数 | 三套口径 |
| 商机 | 大单型才用，可选 | 一级导航放了一个“未启用”占位 |

## 3. 为什么用起来“偏开发方向”：页面排查

1. **信息架构按系统分，不按工作分。** 一个销售要在三个入口间切换：分享访问记录、线索、客户（9 个栏目）。客户管理的 9 个栏目是：主管待处理、我的提醒、客户驾驶舱、客户档案、客户公海、跟进待办、企微同步、账号与权限、小程序咨询线索，把系统配置（企微同步、账号与权限）和日常工作（待办、提醒）混在一起（`customerManagement.tsx` 的 `titleOf`）。
2. **文案在讲数据口径和技术约束。** 例如：
   - 线索页正文：“全平台小程序线索概览，不随下方队列、用户或搜索条件变化。待处理为新线索与跟进中；高意向仅计待处理线索；今日新增按服务端统计日期计算。”（`customerLeads.tsx:401`）
   - “会话或客户接入状态尚未确认，暂不能修改线索。请重新检查会话。”（`customerLeads.tsx:160`）
   - 访问记录：“按北京时间自然日统计 · 包含全部保留期内的数据”，快照信息（as_of / metric_version），页头常驻「意向规则与重算」按钮，「统计口径与限制」说明段。
   - 线索详情里的“任务号 / 会话号”；行为时间线里的“命中知识库回答”“进入 AI 兜底回答”（`customerLeads.tsx:128-131`）。
3. **列表缺少销售真正关心的信息**：从哪个内容、经谁分享来的；最近看了什么；上次联系是什么时候、说了什么。分享线索的需求摘要只是一句统计句。
4. **操作不顺手。**
   - 负责人是自由文本输入，不是选人（`customerLeads.tsx:817`）；
   - 负责人筛选只有“全部 / 未分配”（`:526`），来源筛选只有“分享意向”（`:530`）；
   - 跟进弹窗必须同时选状态、写备注，没有“已电话 / 已加微信 / 约见面”这类快捷结果，也没有一键拨号、复制微信；
   - 线索上可以直接选“已成交”。
5. **意向标签不可信**：访问记录写“中意向参考”“低关注待观察”，线索写“高意向”，客户写“高”，三处三套口径。
6. **高频入口落在只读页**：「销售线索」分组的落地页是 `/customer-leads`，带待处理角标（`navConfig.ts`，`landing: '/customer-leads'`）。但在 CRM 模式下，这个页面只读，顶部提示“前往客户档案列表”。
7. **「商机」以“未启用”卡片占着一级导航位。**
8. **来源名直接显示代码**：`sourceLabelMap` 缺 `customer_service`（后端默认来源）、`share_tracking_auto` 等取值，会直接显示英文代码（`customerLeads.tsx:60`）。
9. **用词**：访问记录把访客叫“客户视角”，访客卡片上看不到“谁分享给他的”。

## 4. 建议的目标模型

### 4.1 一条漏斗、一套词

| 阶段 | 定义 | 进入方式 | 出口 | 在哪里看 |
| --- | --- | --- | --- | --- |
| 访问动态 | 某人打开了分享内容 | 自动记录 | 达到阈值后自动成为线索 | 挂在线索 / 客户详情的“动态”里；内容效果报表留给运营 |
| **线索** | 待验证的信号 | 主动咨询或留资、企微新好友、访问达到阈值、完成预算测算并留电话；也可手动新建 | 转为客户 / 无效 | 线索池。状态：待分配 → 待联系 → 跟进中 → 已转客户 / 无效 |
| **客户** | 确认有真实建房需求、能联系上、有负责人 | 线索转客户（= 补齐 5 项 + 确认归属），或顾问手动报备 | 成交 / 暂缓 / 无效 / 公海 | 客户档案。阶段：初步沟通 → 方案出图 → 报价 → 签约成交；暂缓 |
| 成交 | 主管确认凭证 | 保留现有规则 | — | 客户档案 |

“商机”不单独建；建房通常一个客户对应一个项目，用客户阶段承担商机的作用即可。

### 4.2 三类来源怎么进

| 来源 | 进入为 | 负责人 |
| --- | --- | --- |
| 分享内容访问（已登录） | 达到阈值自动生成线索，或销售手动转 | 分享人是员工的，就归分享人；分享人是客户或设计师的，进待分配，并记录“转介绍人” |
| 分享内容访问（匿名） | 不直接成为线索；在被分享页加“领取完整预算 / 免费精算”授权手机号按钮，识别后合并历史轨迹，再成为线索 | 同上 |
| 企微新好友 | **线索**（来源 = 企微），不直接当客户 | 添加好友的员工 |
| 客户主动留资（转人工、咨询、测算后留电话） | 线索，标为高优先 | 待分配，或按渠道规则分配 |
| 静默需求草稿、点击生成 | **不再生成线索**，只记行为动态，参与加分 | — |
| 顾问手动报备 | 可直接成为客户（顾问已经当面确认过） | 报备人 |

### 4.3 意向度合成一个分数

线索和客户共用一个可解释的分数，同时保留“原因”列表：

- 行为：访问次数、累计停留、看过预算 / 方案、转发、收藏；
- 资料完整度；
- 主动动作：咨询、留电话、加企微。

现有 tracking 规则体系已经支持版本化和重算（`intent-rules.md`），把“停留时长”“预算 / 方案查看次数”加入参与指标即可，不需要推倒重来。

### 4.4 让预算卡片真正可追踪

- 分享路径带上结果 ID，或者生成一个只读的“预算卡片”快照页，让对方打开看到同一份预算；把这个页面设为公开采集页。
- 页内放“我也测一份”“找顾问要详细报价”按钮，把浏览转成留资。
- 访问动态里显示“看了《泉州 200㎡ 三层 预算 58 万》3 次，共 4 分钟”。
- 注意：预算结果属于分享人的个人数据，快照页对外展示到什么粒度，需要产品和隐私一起确认。

## 5. 分阶段改造路线

**P0（1–2 周：主要改命名和入口，不动数据模型）**

1. 统一用词：访问记录「客户视角」改为“访客”；CRM 的 `pending` 对外显示为“线索 / 待确认”；客户档案默认只显示已确认客户。
2. 「销售线索」落地页改为可操作页：CRM 模式下直接进入 CRM 的待确认线索队列；隐藏「商机」卡片。
3. 文案去技术化：把统计口径、快照、规则重算收进“设置 / 更多”；详情去掉任务号、会话号；时间线改成业务语言。
4. 修正前后端门控不一致（身份为空且客户内容占比 ≥70% 的访客也显示转化按钮）；补全来源名称。
5. 负责人改成下拉选人；跟进弹窗加快捷结果。

**P1（2–4 周：打通链路）**

6. CRM 模式下开放“访客 → 线索”：走 CRM 的 ingest 生成待确认线索，不再返回 409；分享人是员工时带入负责人。
7. 停止静默生成线索（`structured_requirement` / `generate_click` 改为只记事件）；同步到 CRM 时排除 `invalid`。
8. 把访问动态嵌进线索 / 客户详情（复用现有 visitor contents / sessions 接口）；线索列表增加“来源内容”“分享人”“最近看了什么”三列。
9. 意向规则加入停留时长、预算查看等指标。

**P2（1–2 个月）**

10. 预算卡片快照页 + 留资按钮；匿名访客登录后合并轨迹（可复用 tracking 已有的“匿名会话可信登录关联”能力）。
11. 企微侧素材雷达：员工在企微里给客户发素材时带员工归属，客户打开后实时提醒员工。
12. 统一意向分；线索池自动分配，超时回收（例如 48 小时未联系回池）。
13. 下线旧的 `customer_leads` 工作台，只保留 CRM 一套。

## 6. 需要业务拍板的问题

1. “客户”的定义：是否确认采用“确认有效需求即为客户，成交是客户的阶段”？
2. 企微新好友：作为线索（需要确认）还是直接作为客户？建议作为线索。
3. 分享人是普通用户或设计师时，带来的线索归谁：进公共池，还是记在转介绍人名下？
4. 访问自动生成线索的阈值。例如：7 天内 ≥3 次访问，或累计停留 ≥3 分钟，或看过预算卡片 ≥2 次。
5. 预算卡片对外展示的粒度：总价、面积、地区是否展示，是否隐藏分享人信息？
6. 是否保留“商机”？建议不单独做，用客户阶段代替。
