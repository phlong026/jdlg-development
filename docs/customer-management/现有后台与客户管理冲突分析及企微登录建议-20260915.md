# 现有后台与客户管理冲突分析、重复功能梳理及企微登录建议

日期：2026-09-15。依据当前工作区源码检查，包含本次发现的报告企微交付链路。仅分析与提出修正方案，本轮未修改业务代码、未操作生产服务。

## 1 结论

现有整合方案可以继续使用，不必推倒重做。原小程序用户、订单和会员仍由 Go 管理，企微客户由 Java 管理，前端复用原后台，数据没有被直接搬入同一张客户表。

但不能以“前后端都能构建、客户页面能打开”判断没有冲突。当前存在三类问题：

1. 需要处理的技术耦合：企微事件入口共存、CRM 身份请求拖住整个后台、分域部署的跨域请求头。
2. 必须明确的业务重叠：原客服线索也有负责人、跟进、待办和成交状态；两边没有客户关联或跟进移交机制。
3. 尚未接入的使用能力：源雀原仓库有企微 H5 登录，但本次统一后台没有接入；手机响应式页面不等于企微身份免登。

建议保留现有架构，先消除对原业务的影响，再补企微员工登录，最后做最小的线索移交规则；暂不做小程序身份、订单与 CRM 的全面自动合并。

## 2 哪些内容重复，哪些是合理分工

| 对象 | 原系统管理什么 | 新 CRM 管理什么 | 判断与边界 |
| --- | --- | --- | --- |
| 用户管理 / 用户360 | 小程序 user_id、账号、手机号、会员、订单、AI任务 | external_userid 对应的企微客户 | 对象不同，可以并存；同一个自然人可能出现在两边，当前不会自动识别为同一人 |
| 客服线索工作台 | 小程序咨询、结构化建房需求、来源任务、负责人、跟进和待办 | 加企微后的需求、业务负责人、跟进和待办 | 前半段获客可保留；销售跟进存在实质重复，需要规定移交后的唯一操作入口 |
| 原总控台 | 小程序用户、订单支付、会员和运营待办 | 企微客户新增、未安排、逾期、团队客户 | 合理分工；两个“新增”统计不能直接相加，CRM“成交”不能当支付成功 |
| 原手机号授权验证 | 历史字段仍名为 enterprise_wechat_*，现用于手机号授权、部分原业务校验 | 企微真实好友关系及其删除状态 | 语义不同，不能拿 CRM 加好友事件直接覆盖原验证标记 |
| 报告企微交付 | 生成带 State 的加好友入口、验证报告购买者、绑定报告、发送报告欢迎消息 | 保存客户、好友关系、跟进与同步事件 | 可复用同一客户添加事件，但两条处理链路必须都能收到并各自幂等处理 |
| 后台账号与权限 | Go 的管理账号及会话 | managed CRM 账号和员工归属 | 目前复用同一平台账号，不需要第二套密码；但权限维护与 Java 服务可用性仍有耦合 |
| 手机端 | 原后台网页布局 | 同一个 React 客户模块的响应式页面 | 无需再建一套完整手机 CRM；应补身份登录与真机验收 |

源码依据：service/model/user.go 的用户列表明确筛选 miniprogram；customer_service.go 保存 customer_leads、customer_lead_followups；Java Models.java 保存 crm_customer、crm_followup；ImportService 使用 external_userid 建客户，使用客户 ID 与员工 ID 组合保存好友关系。

## 3 需要优先处理的技术问题

### C01：报告交付和 CRM 的企微回调尚未统一，不能直接切换 URL

性质：两个现存实现之间的集成缺口。风险在正式同时启用时触发，尚未检查生产企微的实际事件配置。

当前有以下三类入口：

| 入口 | 当前作用 | 与另外两者的关系 |
| --- | --- | --- |
| /api/v1/wecom/reports/callback | Go 接收加密企微事件，处理报告绑定和欢迎消息；仅模块可用时注册 | 与 Java 都关心 add_external_contact |
| /iycallback/handle | Java 接收加密企微事件，记录客户与好友关系、排队补资料 | 未看到向 Go 报告模块分发事件的实现 |
| /api/v1/miniprogram/wecom/enterprise-wechat/callback | 原 Go 的票据回调，JSON 请求和自定义 X-Enterprise 签名 | 不是原生企微 XML 事件回调，不能直接互换地址或请求格式 |

报告链路依赖 State、ExternalUserID、员工、报告购买者身份及 WelcomeCode。若把实际事件入口只切到 Java，客户可能成功进入 CRM，但报告绑定和欢迎消息没有执行。只保留报告入口且未做其他分发，则 Java 可能依靠补同步得到客户，但不能假定完整收到原事件及删除原因。

也不能把所有事件不加判断地转给当前报告处理器：reportwecom.Service.HandleEvent 对非空 State 会查找报告票据，陌生 State 或不匹配员工会报错。作为统一入口的消费者时，应区分“不属于报告业务”与“属于报告业务但处理失败”，否则普通获客渠道事件会造成无意义重试。

建议：先核查正式企微的接收事件配置及 REPORT_WECOM_ENABLED 实际状态。若两条链路同时启用，优先复用原 Go 作为统一公网事件入口，先可靠保存事件，再按业务分发到报告处理和 Java CRM。新增的内部投递需要认证、幂等、失败重试，不能只是浏览器侧或 Nginx 的负载均衡。报告欢迎消息保留原模块单一发送责任，CRM 本期不新增重复欢迎消息。

验收：通过报告专用加好友入口，既能完成报告绑定与预期欢迎消息，也能产生 CRM 客户；普通渠道客户仍正常入 CRM，不触发错误的报告绑定；重复事件不重复发欢迎消息。报告欢迎逻辑有时间要求，不能等半小时全量同步来补做。

证据：service/route/report.go:326、339；service/reportwecom/callback.go:16；service/reportwecom/service.go:117；service/reportwecom/provider.go:142、228；service/route/miniprogram.go:1431；Java WecomController.java。

### C02：Java 身份查询会拖住原后台页面加载

性质：已从调用顺序确认的实现耦合，本轮未用真实生产故障做延迟测量。

ManagementSessionProvider 在全站先 await getMe()，再 await CRM /context，之后才把 loading 改为 false。ProtectedRoute 在 loading 时不渲染任何受保护页面。Go 调用 Java 的超时是 20 秒。

因此，已经关联 CRM 的平台管理员登录或整页刷新订单、用户等原页面时，Java 响应慢也会拖住原页面，可能等待到桥接超时。没有 CRM 关联的账号一般由 Go 直接返回关联错误，不一定等待 Java，因此不能描述为所有账号必然卡 20 秒。

建议：原平台 /me 成功即允许原后台显示；CRM 上下文单独异步加载或进入客户模块再加载。Java 故障只影响客户模块，不阻塞原订单、会员等操作。

验收：模拟 Java 不可达或缓慢响应，已授权平台管理员仍能及时打开原用户和订单页面；客户模块显示局部错误及重试入口。

证据：background/src/component/ManagementSession.tsx:12—17；ProtectedRoute.tsx:7；service/route/crm_bridge.go 中 crmRemote 的 20 秒超时。

### C03：若沿用前后端不同域名，CRM 请求的预检可能失败

性质：条件性配置兼容问题。同源部署时不触发此问题。

新 wecomCustomers.ts 所有请求都携带 X-CRM-Request，但 Go 的 CORSMiddleware 允许请求头列表没有该字段。若 VITE_API_BASE_URL 指向另一个源，浏览器的 OPTIONS 预检可能阻止真实请求。单独填写 CRM_ALLOWED_ORIGINS 不能代替 CORS 响应头配置。

建议：正式后台优先按现有同源反向代理接 Go；如果生产确实分域，补齐准确的允许源、允许头和 Cookie 配置，并用实际浏览器验收。不要为解决预检改成开放所有源。

证据：background/src/api/wecomCustomers.ts:19；background/src/config/api.ts:2；service/route/cors.go:36。

### C04：新权限表影响全部旧后台账号，属于发布必须项

性质：有意增加的权限规则，不是偶发程序错误；漏迁移会直接影响旧业务。

两组原管理 API 均加入 ManagementAccessRequired。授权表存在后，未登记、停用或未知范围的管理账号会被拒绝；关闭 CRM_BRIDGE_URL 也不会恢复“所有管理账号自动放行”。

建议：发布前列出所有需要保留的原管理员并显式初始化 platform_admin；逐个验收旧登录和关键原业务。新增 crm_only 顾问后，不能直接回退到缺少新权限检查的旧 Go 程序。

原小程序 API 的注册组仍使用原 token 身份验证，本次后台权限中间件未直接加到小程序接口组。原 Go 重启、同机资源占用和数据库故障仍会间接影响小程序，不能据此承诺零影响。

证据：service/route/index.go:150；service/route/management.go:93；crm_bridge.go:45；service/sql/customer_management_bridge_up.sql。

### C05：平台权限修改与 Java 配置仍绑定在一个操作里

性质：管理操作可用性耦合。

账号授权页在 Java 不可用时禁止保存；Go 的保存操作也会调用 Java provision，只有成功才应用最终 scope/enabled。因此纯平台权限调整、启用或恢复账号也可能被 Java 故障阻塞。停用请求的后端准备阶段可以先禁用访问，但界面仍可能无法发起或最终返回失败，需明确操作结果。

建议：将“Go 平台访问授权”与“CRM 角色/员工关联”在服务端拆分为可独立完成的动作。员工停用、平台权限收回优先在 Go 生效，CRM 同步失败时保持禁用并可重试。界面仍可以放在一个账号页，无需再建一套庞大的权限系统。

证据：service/route/crm_access.go 的两阶段保存；background/src/pages/customerManagement.tsx 的 serviceAvailable 保存限制。

## 4 业务重复与建议边界

### B01：客服线索和企微客户都有销售跟进，会产生重复工作

旧客服线索包含 name、phone、demand_summary、intent_level、assigned_to、status、next_followup_at，并有独立跟进历史、批处理和逾期待办。新 CRM 同样维护电话、需求、意向、负责人、阶段、下次联系时间和跟进记录。这是业务能力重复，不能只因为表名不同就说“没有重复”。

例如：客户在小程序提交建房需求，客服线索安排明天联系；客户加企微后又产生 CRM 档案，顾问在 CRM 安排下周联系。当前两边都可能继续显示待办，且备注与阶段互不更新。

轻量方案：旧工作台继续负责小程序需求收集、联系和加企微前的承接；完成人工核对与移交后，销售推进以企微 CRM 为唯一工作记录。旧线索保留来源与历史，不再作为持续销售待办来源。

要让上述规则可靠执行，需要补最小的“已移交”标记/客户引用与队列排除逻辑；当前还没有这个能力。没有做该小改动前，可以制定人工移交登记制度，但不能宣称两边会自动联动。已转交不能用“已成交”状态代替。

不建议现在复制旧建房字段、AI 来源任务和客服漏斗到 Java，也不建议按手机号或昵称自动合并两套客户身份。

证据：service/model/customer_service.go:218、257、623、791；Java Models.java、CustomerService.java；background/src/pages/customerLeads.tsx。

### B02：顾问与小程序线索的权限不连通

crm_only 顾问不能访问原 customer-leads API，前端也不给它“线索”页签；旧线索 assigned_to 是字符串，并不是新的企微员工权限模型。

这是当前防止越权的合理限制，但如果让同一个顾问承接小程序咨询，就会出现“线索写了他的名字，他仍打不开”的工作流断点。不能为了方便而直接把顾问升级为 platform_admin，因为这会同时开放订单、配置等原模块。

一期可由原平台运营人员负责线索移交，顾问只在 CRM 跟进。后续确需顾问自己处理线索时，再给旧线索增加本人归属的数据权限及受控入口。

### B03：手机号授权、企微好友关系、报告解锁是三套状态

旧 users.tsx、userWorkbench.tsx 已将 enterprise_wechat_verified 呈现为“手机号授权验证”；user_profile.go 的找回流程也依赖对应手机号状态。它不应被新 CRM 的加好友/删好友状态覆盖。

报告则有 building_reports.bound 和 external_user_id，并由报告链路验证购买者、UnionID 与实际好友关系后绑定。Java 当前没有写该报告表。

建议统一业务文案并分别显示“手机号已验证”“企微好友关系”“报告已绑定/可交付”，数据仍由各自的验证链路负责。客户删企微不能顺带抹掉其手机号验证；普通客户添加也不能自动认定为某位小程序报告购买者。

证据：background/src/pages/users.tsx:370、723；service/route/user_profile.go:122；service/report/service.go:136；service/report/mysql_store.go:138；Java ImportService.java。

### B04：负责人不一定是“正在和客户聊天的那位员工”

CRM 以 ownerId 决定顾问可见范围，好友关系单独保存在 iyque_customer_info。一个客户可添加多位企微员工；新客户初始归属由事件或同步规则给出，主管也可以手工调整。同步明确不覆盖人工负责人、阶段和待办。

所以“员工 B 加了这个客户”不保证 B 在 CRM 中可见；客户仍可能归员工 A。员工失效后，其客户也不会自然变成已分配给其他顾问的客户。

建议把页面字段明确称作“业务负责人”，详情另外显示“企微好友关系”；员工离职或授权范围缩小时，由主管检查与交接其客户。不要把两者当成一个状态。

### B05：菜单、统计与成交口径需收敛

原侧栏保留“客服线索工作台”，CRM 内又以“小程序咨询线索”嵌入同一组件。这是同一能力的双入口，不是重复开发了第二套线索后端。为减少误会，建议确定一个主入口，旧 URL 保留兼容跳转。

原总控台按小程序用户和真实订单统计；CRM 按企微客户统计，新旧新增量不能直接相加。旧线索 converted、新 CRM won 都是人工业务状态，不能直接增加订单金额或改变会员权益。总控台继续展示经营数据，客户驾驶舱展示销售跟进即可。

证据：background/src/component/sidebar.tsx:48、78；customerManagement.tsx:47—48；service/route/dashboard_management.go；service/model/customer_service.go；Java CustomerService.java。

## 5 关于“应该直接用企微授权登录吗”

### 5.1 回答

对顾问和客户主管而言，企微身份登录更符合手机日常办公习惯，建议接入。完成配置后，手机从企微工作台打开本企业的 H5 应用是可行的产品形态；腾讯官方的企业内部应用接入示例也采用自建应用、可见范围、可信域名及 PC/H5 登录配置。[腾讯云企业内部应用说明](https://cloud.tencent.com/document/product/1301/84599)

但需要区分以下三件事：

| 用户所说的“授权” | 实际作用 | 是否被一次员工登录替代 |
| --- | --- | --- |
| 员工企微身份登录 | 确认访问后台的是哪个企业成员 | 这是应新增的登录入口 |
| 系统读取企微客户 | 允许服务端调用客户联系 API，并接收业务事件 | 不能，仍需企业管理员配置权限、凭据与事件接入 |
| 本系统权限授权 | 决定该员工能看本人客户、全团队，或原后台其他业务 | 不能，登录成功不等于获得全部后台权限 |

外部客户加了公司企微，不应因此获得管理后台登录资格。登录的对象是企业员工，客户是被管理的业务对象。

### 5.2 当前到底实现到了哪里

源雀原仓库已有 IYqueLoginController.weComLogin 和 weComRedirect，也有 frontEnd/mobile 的授权流程。因此不是没有可参考的开源实现。

但本期 phase1/pom.xml 仅编译列出的 phase1 与少量共享类，未包含原 IYqueLoginController；统一 React 登录页调用的是 Go 账号密码登录，当前 Go 中也未找到对应员工 OAuth 登录入口。所以当前版本支持手机网页操作，尚不支持我们这个统一后台的企微身份免登。

原源雀返回独立 JWT，而现在统一后台使用 Go 会话、management_access 和 managed CRM 账号。不能为了“已有手机登录”就把旧控制器和旧手机站整体发布，否则会重新引入另一套认证和权限入口。

旧实现中的固定 state、授权跳转目标、请求的个人信息范围，也应按本系统需求重新校验；本次需求只是识别员工，无需默认扩大到收集更多个人资料。

### 5.3 建议的终端体验

| 使用场景 | 建议入口 | 说明 |
| --- | --- | --- |
| 手机企业微信内 | 工作台“客户管理” → 员工网页授权 → CRM | 优先实现，尽量做到打开即进入本人工作台；具体授权交互以应用配置和客户端为准 |
| 电脑浏览器 | 原登录页新增“企业微信登录” | 可采用扫码/官方登录组件；扫码识别后仍核对平台权限。腾讯官方产品也采用企微扫码确认登录。[官方扫码登录示例](https://cloud.tencent.cn/document/product/378/43080) |
| 手机普通浏览器 | 提示从企微打开，保留已有账号登录作为兜底 | 不把“在企微内可授权”等同于“所有手机浏览器都可静默登录” |
| 外部客户的微信 | 不提供员工后台登录 | 保持客户侧小程序及原业务入口 |

无需重做手机 APP，也不必重新启用源雀原来的整套 Vue 手机界面。沿用现有 React 页面和 Go 会话，可保持电脑、手机一致。

### 5.4 与现有权限兼容的最小接入设计（建议，尚未开发）

1. 企业管理员配置“客户管理”自建应用，设置实际使用员工范围、应用首页、可信域名和授权回调。员工登录凭据与客户联系凭据按用途分别核对，不把已有 WECOM_CONTACT_SECRET 自动视为登录所需的全部配置。
2. Go 增加登录发起与回调处理，校验一次性 state 和授权码，在服务端换取成员身份。只允许预先登记的企业，不接受前端直接提交一个员工 ID 就登录。
3. 用“企业 ID + 员工 UserID”唯一映射到 Go 管理账号。初期由管理员预绑定/预批准，未授权成员进入“尚未开通”页面，不自动成为平台管理员。
4. 身份通过后复用原 Go 会话，同时检查账号启用状态和 management_access；CRM 继续沿用 managed 账号与 ownerId 数据权限。
5. 前端调整登录完成后的会话初始化。当前 ManagementSession.tsx 先检查 localStorage 中的 admin_token 标记；如果 OAuth 只写了 Cookie，没有相应初始化，仍可能被当作未登录。应以服务端会话核验为准，不能仅设置本地标记就视为登录成功。
6. 手机进入顾问客户列表/待办；主管进入客户驾驶舱。原平台管理员保留原后台入口，按原权限使用其他业务。

当前 crm_account.employeeId 没有唯一约束，且主管可以不绑定业务员工，因此不能简单用“按 employeeId 查到的第一条 CRM 账号”作为登录映射。员工认证身份与客户业务归属应明确区分，并对账号映射做唯一性校验。

同时处理现有登录页的“记住密码”行为：当前会把明文密码写入 localStorage，这是旧登录实现的问题，不是本次 CRM 新增。手机共用设备场景更容易暴露这一问题，建议保留账号记忆，取消保存明文密码。

## 7 本轮验证与结论边界

本轮阅读了 React 登录/会话/路由/侧栏、旧客服线索、新客户模块、Go 管理权限/桥接/原验证回调/报告企微链路、Java 客户同步/授权及原源雀 H5 登录代码。
