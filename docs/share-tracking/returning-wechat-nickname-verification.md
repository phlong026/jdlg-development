# 旧微信账号再次登录补全昵称

> 历史验收记录。下文“稍后填写继续浏览”已由[2026-10-29 统一资料门禁](profile-access-remediation-20261029.md)替代；新旧用户均须补齐昵称和头像。

目标为找回已验证微信身份对应的原 `user_id`，读取服务端资料；空白或超过32码点的无效昵称提示用户使用原生昵称填写能力确认，PUT保存到同一账号并GET回读。已保存的有效昵称优先复用，不用空值、旧缓存或其他账号迟到响应覆盖。用户可稍后填写，阅读不强制披露。`wx.login`只提供登录凭据，不自动返回真人昵称。

## 实施及可验证结果

- `cc51bbc` 已处理已有token恢复补检、欢迎弹窗后续检、账号隔离的稍后填写、原生form最终值保存及回读。再次微信登录按服务端openid/unionid查已有账号，不通过昵称或设备猜测合并账号。
- 本轮补缺：服务端profile昵称有效性与保存规则一致；同账号有效服务端昵称可刷新旧缓存，空值不覆盖缓存；token或资料ID变化时拒绝应用旧响应。前端两套TS/JS新增6项，共50项昵称/登录聚焦回归通过。
- 实际HTTP隔离闭环：旧号空昵称→合成Code2Session提供同微信身份→实际POST登录返回原ID且非新用户→实际JS请求签名、PUT昵称和GET回读→换设备再次登录仍同ID同昵称→旧token、后台ListManagementUsers和原visitor user_id的实际profile resolver均读取新昵称。通过0.529秒；不是原生昵称选择验收。
- 小程序全部439项：436通过、3项需微信编译器而skip；专项267/267，生成一致性和59路由门禁通过。后台模块在会话来源补修后746项通过；最终新增显示补修再统一回归。

实际HTTP测试源、执行命令和脱敏日志位于 `/workspace/jdlg-user-list-audit`：`returning_wechat_nickname_test.go`、`returning-wechat-tests.log`、`REPRODUCE.md`。该诊断使用临时Go overlay、miniredis和无外网MySQL，所有外呼被拦截；没有使用生产账号/数据库，专用容器已清理。原生选择/审核/blur/submit的时序由用户按独立探针和真机清单自测。

## 后台批量默认名的审计

实际7类账号模型/后台HTTP共14个夹具断言、前端adapter/convertRow/formatter3项验证：未发现全局丢弃nickname字段。普通有效名正常，缺profile、NULL、空串和纯空白均保留账号行。新建空资料、选填流程中断、未绑定登录方式另建号可以广泛产生空昵称，但没有生产统计证明占比。

另确认窄条件显示缺陷：真实profile昵称以wx_开头时被错误当作生成登录名过滤。该显示层修复只让可信nickname字段直接trim后优先显示，保留username/display_name兜底过滤；不改变认证、账号归属或历史数据。不能据此前缀推断大面积根因。

只返回数量/日期的只读核验SQL见同目录 `user-profile-readonly-audit.sql`；只在隔离夹具验证，未在生产执行。昵称分类互斥，微信/手机号/密码凭据分布可重叠；按账号创建日看当前状态，不能据此还原历史因果。

同一u:user_id的旧访问查询会动态读取当前profile，保存后刷新即可更新；没有保存过的真实昵称、A/B拆号、无可信identity_link的匿名记录，不能自动恢复、合并或迁移。真实用户截图中的原因尚未获生产证实。
