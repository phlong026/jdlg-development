# 分享访问系统：第二轮完整代码评审（2026-10-13）

基线：`28520dc`（PR #5 合并后）。范围：`service/tracking`、`service/route/share_tracking*.go`、小程序 `utils/tracking`、后台 `pages/shareTracking` 与 `api/shareTracking.ts`。

本轮评审的重点不同于前几轮。前几轮集中在正确性、隐私和权限边界，这些方面的实现质量很高。本轮重点检查**真实流量和真实部署下能不能用**：容量、锁、连接池、部署配置和运维入口。

## 结论

权限边界、隐私处理、幂等和计量口径做得扎实，自动化覆盖充分。但有 **2 个 P0、4 个 P1**，会让系统在很小的真实流量下就无法使用，或者让整个业务服务受影响。这些问题必须在上线前、最好在联调前解决；不解决的话，联调得出的性能和稳定性结论没有意义。

| 级别 | 编号 | 问题 | 影响 |
| --- | --- | --- | --- |
| P0 | R1 | 列表查询读取原始事件，2 万条预算很快耗尽（已实测） | 7 天内约 400–600 次一分钟访问后，访客列表返回 422 |
| P0 | R2 | 所有跟踪请求串行通过同一行租户锁，且与主业务共用 20 连接池 | 并发时排队；锁内还有 CRM HTTP 调用（最长 20 秒），可能拖垮整个后端 |
| P1 | R3 | 反向代理后默认不信任转发头，全部用户共用每分钟 60 次入口额度 | 生产部署后大量 429，采集基本失效 |
| P1 | R4 | 保留期清理没有可执行入口，且试算读取全表，超过 2 万行即失败 | 90/180 天保留政策无法执行 |
| P1 | R5 | 个人数据删除也受 2 万条预算限制 | 重度用户的删除请求会失败 |
| P1 | R6 | 设备时钟偏差超过 2 分钟时，事件被全部拒绝且被 SDK 丢弃 | 部分用户数据静默为零 |
| P2 | R7–R11 | N+1 查询、无索引扫描、每批重建汇总、业务回执在锁下 500ms 超时、删除墓碑永久阻断 | 性能和统计偏差 |
| P3 | R12–R14 | 分享令牌明文留存、媒体列表忽略分页、小程序码缓存写入非原子 | 小问题 |

## P0

### R1 查询预算在很小的数据量下就会耗尽（已实测）

**位置**：`tracking/query.go` 中的 `factsSelected`；`tracking/scoped_store.go:13`（`maxQueryRecords = 20000`）

**问题**：访客列表、素材列表、会话轨迹都要读取窗口内的**原始事件**，然后再按会话把完整会话的事件**再读一遍**。两次读取都计入同一个 2 万条预算。小程序 SDK 每 10 秒上报一次 `visible_segment`（`core.ts` 中 `HEARTBEAT = 10000`），所以一次 1 分钟的可见访问大约产生 8 条事件，查询时消耗约 16 条预算。日汇总（`daily_summary`）只在原始数据过期（90 天）后才参与查询，近期查询完全读原始事件。

**实测**：在内存仓库中模拟每次访问为 1 次 PV、6 个 10 秒分段、1 次结束事件，然后查询访客列表：

| 窗口内访问次数 | 访客列表 |
| --- | --- |
| 200 / 400 | 正常 |
| 600 及以上 | 422“查询范围过大” |

后台默认窗口是 7 天（`shareTracking/model.ts` 中 `range: '7'`），也就是说**每天约 60–85 次一分钟访问**，默认首页就打不开；“全部”（180 天）会更早失败。PRD 的目标是 10 万 PV/日，差了三个数量级。

**建议**：
1. 接收事件时，在同一事务中维护**每个 PV 一行**的汇总投影（可见时长、最后活动时间、是否计数），列表只读投影，不读原始事件。
2. 列表的计数、排序和分页改成 SQL `GROUP BY` 加 keyset 分页，原始事件只在展开单个 PV 的轨迹时读取。
3. 2 万条预算保留作为安全上限，但不能作为常规路径的容量。

### R2 全局租户锁 + 共享连接池，锁内有外部 HTTP 调用

**位置**：`tracking/store.go:34-57`（`SELECT ... FOR UPDATE` 锁 `tracking_tenant_lock`）；`component/database.go:38`（`SetMaxOpenConns(20)`）

**问题**：
- 每个跟踪事务都先锁同一行。生产只配一个 `TRACKING_TENANT`，所以**整个跟踪系统完全串行**。走这把锁的不仅是事件上报，还包括：
  - 后台所有只读查询，单次最多读 2 万行；
  - 公开阅读页正文（`ReadContent`）；
  - 公开媒体，每张图片、每次视频 Range 请求都会触发一个加锁事务（`Service.Media`）；
  - 分享解析（`ResolveShare`）。
- 跟踪使用的是 `users.DB`，与主业务共用 20 个连接。等锁的事务会一直占着连接，并发稍高时主业务（订单、登录等）也拿不到连接。
- **锁内有外部 HTTP 调用**：`LinkCRM` 和 `VisitorCRMTarget` 在事务内调用 `crmRemote`。HTTP 客户端超时是 20 秒，`LinkCRM` 也没有另设更短的超时（`VisitorCRMTarget` 设了 2 秒）。CRM 慢一次，全站跟踪就停 20 秒。
- 收藏和咨询的回执在后台 goroutine 里以 500ms 超时执行（见 R10），锁竞争时会**系统性**丢失，而不只是偶发少计。

代码注释已经说明“性能是发布门槛，分析后再改成分区行锁”，但从上面的范围看，这个问题不能留到压测阶段再处理。

**建议**：
1. 只读路径（后台查询、公开阅读、媒体、分享解析）不加租户锁，改用一致性快照读（`REPEATABLE READ` 或 `START TRANSACTION WITH CONSISTENT SNAPSHOT`）。
2. 写路径把锁粒度降到会话或访客：幂等改为依赖主键唯一约束（`INSERT` 冲突即视为重复）；删除墓碑检查加行锁。
3. 外部 CRM 校验移出事务：先校验，再开一个短事务，在事务内复核本地状态后写入。
4. 跟踪使用独立的连接池，或者加并发信号量，保证跟踪流量不会占满主业务连接。

## P1

### R3 反向代理后的限流默认是全站共享

**位置**：`route/share_tracking_limiter.go:136-146`

不配置 `TRACKING_TRUSTED_PROXY_CIDRS` 时，限流按 socket 的 `RemoteAddr` 计算。部署在 Nginx 或宝塔反向代理后面时，所有用户的 `RemoteAddr` 都是代理地址，**全站共享每分钟 60 次 `/entry`、60 次 `/shares`**，超出就返回 429。这个设计是有意的安全默认，但后果很严重，而且现在不会有任何提示。

**建议**：启动时如果检测到采集已开启但没有配置可信代理，打印明确的告警日志；把这一项列入上线检查表（已写进[联调清单](integration-env-checklist.md) 3.11）。另外，移动网络的运营商 NAT 下，60 次/分钟/IP 也偏紧，建议同时按客户端随机 ID 限流。

### R4 保留期清理无法执行

**位置**：`tracking/governance.go:48-60`（`retentionCandidates`）、`:97`（`PurgeExpired`）

- `PurgeExpired` 和 `PlanRetention` 在整个仓库中**只有测试调用**：没有 HTTP 路由、没有 `cmd/` 工具、也没有定时任务。文档写的是“维护操作员执行”，但操作员没有可以运行的入口。
- `retentionCandidates` 对每类记录调用 `r.List(kind)`，这是**不带时间条件的全表读取**，再在 Go 里按时间过滤。任意一类记录超过 2 万行，试算就返回 422。按 R1 的数据量估算，事件表几百次访问后就会超过 2 万行，此后保留期永远无法执行。
- 清理在单个事务中逐行 `DELETE`，并且持有全局锁。

**建议**：新增 `cmd/tracking-retention` 工具；SQL 层按 `occurred_at < ?` 筛选；按时间片分批计划和执行（每批生成自己的审核摘要），每批独立短事务。

### R5 个人数据删除受预算限制

**位置**：`tracking/privacy_query.go:121`（`planVisitorDeletion`）、`tracking/privacy.go`（`DeleteVisitor`）

删除计划在一个事务中读取该访客全部类别的记录，受 2 万条预算约束。一个活跃用户几个小时的可见时长（每个分段对应事件、事件哈希、序号三行）就可能超限，删除请求返回 422。这是合规路径，不能因为数据多就失败。

**建议**：先写墓碑（立即阻断新数据和旧队列重放），再分批删除并记录进度，全部完成后才返回 `completed`；后台显示“删除进行中”。

### R6 时钟偏差导致事件被静默丢弃

**位置**：`tracking/service.go:331`；小程序 `core.ts:36, 154`

服务端要求事件时间在 `[服务器时间 - 72 小时, 服务器时间 + 2 分钟]` 之内，并且不早于会话开始（服务器时间）2 分钟。事件时间直接取手机墙钟（`io.wall()`）。手机时间偏差超过 2 分钟时，这台设备的每条事件都会被拒绝；SDK 收到 `rejected` 后从队列删除，只在本地诊断里加一个计数。后台看到的效果是“这个用户没有访问记录”，没有任何报错。

**建议**：批次请求附带客户端发送时的墙钟时间，服务端计算偏移量后校正事件时间（单调时钟差值不受墙钟影响）；或者服务端记录被拒原因的聚合计数，并在诊断中可见。

## P2

### R7 N+1 查询与无索引扫描（都在全局锁内）

- `factsSelected` 对每个会话单独执行一次 `r.Get("identity", session)`。
- `validateEvent` 对**每条事件**都调用 `available()`。旧业务路由每次还要通过 `resolveLegacy` 查询原业务表，一个 50 条的批次就是 50 次查询。
- `share_intent` 校验用 `scopedRecords(r, "share", Shares: [...])` 查询。但 `recordShareColumn("share")` 返回的是 `JSON_EXTRACT(payload,'$.share_id')`，用不到 `tracking_share_time` 索引，每条分享事件都会扫描租户全部分享记录。新写入的 share 行其实已经填了 `share_id` 列（`service.go:305`），JSON 表达式只是为了兼容旧行。
- 访客筛选的 `EXISTS` 子查询同样依赖 `JSON_EXTRACT`。

**建议**：批量读取 identity；每个批次对 `(route, content, version)` 只校验一次可用性；新行查询改走 `share_id` 列，旧行做一次回填迁移。

### R8 每个批次都重建整个会话的汇总

`Accept` 结束前调用 `RebuildSessionSummaries`，读取该会话的全部事件重算日汇总。SDK 每 10 秒刷新一次队列，一个会话的总开销随时长平方增长。建议改为增量更新，或者只在 `page_end`、会话结束和定时任务时重建。

### R9 删除墓碑永久阻断，且留存原始标识

`Enter` 和 `CreateShare` 发现访客有 `deletion` 墓碑就返回 410。墓碑的 `record_id` 是原始的 `u:<用户ID>`，没有过期机制。也就是说，被删除的用户**以后永远不会再被记录**，他分享出去的链接也拿不到归因。这可以理解为“不再追踪我”，但属于产品和合规决策，需要业务确认。另外，墓碑建议存哈希而不是原始 ID。

### R10 业务成功回执在锁竞争下系统性丢失

收藏（`route/favorite.go:128`）和咨询（`share_tracking_consultation.go`）的回执在 goroutine 中以 500ms 超时执行事务。R2 的全局锁只要有一个慢查询，回执就会超时。跟进参考标签依赖这些回执，所以高峰期会**系统性**低估意向，而不是偶发少计。R2 解决后这个问题会大幅缓解；在此之前，建议至少记录超时计数。

### R11 多归属能力取交集，可能出现意外降权

`loadTrackingScope` 对多个归属的能力取交集。比如账号在 owner-1 有 view+manage、在 owner-2 只有 manage，最终 `View=false`，连 owner-1 的访客都看不到。文档说明这是有意为之，但联调配置权限时很容易误判为 bug，需要在权限矩阵中明确说明（已写进联调清单第 4 节）。

## P3

- **R12**：`share_request` 记录的 payload 里保存了明文 `share_token`（`service.go:309-313`），而 `share` 记录特意用 `hash(token)` 作主键。数据库只读权限就能拿到可用的分享令牌。幂等重放只需要返回 `share_id` 和过期时间，或者存加密后的令牌。
- **R13**：后台 `tracking.media()` 传了 `cursor` 和 `limit=20`，但 `ListMedia` 忽略这两个参数，返回全部媒体（同样是全表读取，受 2 万条预算限制）。
- **R14**：小程序码缓存用 `os.WriteFile` 直接写目标文件。并发请求可能读到写了一半的文件；缓存文件每天按账号和素材新建一份，从不清理。建议先写临时文件再 `rename`，并加清理任务。

## 做得好的地方

- 身份、租户和归属全部由服务端注入，严格 JSON 解码并拒绝未知字段，写操作有自定义请求头加 Origin 双重校验，所有响应 `private, no-store`。
- SQL 全部参数化，列名是固定字符串；超大 payload 不会被读进 Go 内存；预算超限时整个事务回滚，不会返回半份统计。
- 媒体上传：类型嗅探、尺寸校验、随机文件名、`O_EXCL` 创建，下载带 `nosniff` 和 `default-src 'none'`。
- 富文本白名单、事件幂等（`event_id` 指纹 + 分段序号）、迟到和乱序处理、删除墓碑防重放，这些都有专门的回归测试。
- 跟踪故障不影响原业务（fail-open），采集默认关闭。
- 文档始终严格区分“自动化已覆盖”和“真实验收通过”。

## 建议的处理顺序

1. **联调前**：修 R3（启动告警，或至少在部署清单里明确写出）；R6 加诊断计数。这两项改动小，但不改的话联调数据会失真。
2. **联调期间并行**：R2 只读路径去锁，外部 CRM 调用移出事务；R1 加 PV 级汇总投影。这两项是架构改动，需要单独开 PR 并补测试。
3. **上线前**：R4/R5 的分批清理和删除工具；R7/R8 的性能修正，然后再做压测（AT-17）。
4. **业务确认**：R9 墓碑策略、R11 权限交集。
