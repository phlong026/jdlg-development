# 后台管理改造 · 影响面与回归分析（改造前置）

- 日期：2026-10-06
- 目的：动手改造之前，先弄清三件事——**改造会碰到什么、会弄坏什么、现在已经坏了什么**，并给出让改造后"能正常使用"的验证与发布方案。
- 对象：按 [后台管理优化分析报告](./后台管理优化分析报告-20261004.md) §2 的 9 组导航方案改造 `JDLG/background`（后台前端）。
- 关联：仿真稿 `designs/jdlg-admin-redesign/`；复现脚本 `docs/后台改造-分析脚本/`。

---

## 0. 结论

1. **最大的风险来自"网址会变"，而不是"导航会变"。** 入口从 25 项精简为 9 组，本质只是导航分组；页面网址完全可以原样保留。只要网址不变，下文 R-1 ～ R-4 四类高风险（样式整页失效、52 处硬编码跳转、查询参数契约、外部系统写死的旧网址）**同时消失**。
   **仿真稿里的新网址（`/orders/virtualpay`、`/crm/pool` 等）只是演示用，实施时不要照搬。**
2. **现役页面的前后端接口契约是一致的**：前端 125 处调用中 113 处与后端路由完全对上，其余 12 处全部来自两个已废弃的模块（`gifts.ts`、`products.ts`）。
3. 确认了 **16 项现存缺陷**（§4）：其中 6 项小而确定，建议改造前先修（D-1、D-2、D-3、D-5、D-6、D-11）；2 项需要你做业务判断（D-4、D-13）；其余随改造或独立排期。
4. **前端没有任何自动化测试。** 没有基线，改造就无法证明"没弄坏"。本机看起来具备搭联调环境的条件（Docker Desktop 在运行；本机有 Playwright 命令和 Chromium 缓存，可用性待实测）。
5. **发布前必须登记管理员权限种子**：`management_access` 表一旦存在，未登记的账号一律被拒绝。使用者 10 人以上，漏登记就是整队被锁在门外。
6. **关于"保证所有 bug 都修复"：** 静态分析只能给出已知清单；未知的缺陷只能靠联调环境、E2E 冒烟和灰度发现。能做到的是三件事——已知的全部修复；改造引入的回归有自动化拦截；出问题能一键回退。

## 1. 分析做了什么、没做什么

| 维度 | 方法 | 产出 |
|---|---|---|
| 页面与网址的耦合 | 全量检索 `navigate(`、`<Link>`、`window.location`、`useSearchParams`、`data-admin-page`、数据结构里内嵌的 `path:` | §3 R-1 ～ R-3 |
| 后端/部署层对前端网址的依赖 | 检索 Go 源码、部署手册、Nginx 示例、CRM 文档中的 `/admin` 引用 | §3 R-4、R-9 |
| **前后端接口契约** | 脚本：用 esbuild 求值 `config/api.ts`，解析前端全部 `get/post/put/patch/del` 调用；解析 Go 源码还原管理端路由表（含 `Group` 嵌套前缀）；逐条比对 | 125 条前端调用、128 条后端路由，差异见 §4 |
| 同类缺陷扫描 | 扫描管理端请求结构体中加在 `bool`/数字上的 `binding:"required"`（零值陷阱）；扫描定时器/监听器清理、`key={index}`、未捕获 Promise | §4 |

**没有做（请知悉）：**
- 没有启动真实后台和后端，没有连数据库，所有结论来自代码与命令输出；
- 没有逐页深读全部 34k 行前端代码——26 个页面中，只对"与改造相关的耦合点"做了系统检索，对其余业务逻辑只做了抽样阅读；
- 没有审查 Java CRM 内部实现和小程序端；
- 页面使用频次仍是推断。

## 5. 对原方案与仿真稿的修正

分析之后，我建议把方案调整为以下几条，其中第 1 条是最重要的：

1. **网址不变，只改导航。** 分组页的 Tab 直接指向现有网址（`/virtualpay`、`/designer-center` 等）；"虚拟支付监控"仍在 `/virtualpay`，只是侧栏不再单列、而是出现在"订单与支付"分组的 Tab 里。网址是否统一重命名，作为一个可以**以后单独做**的独立决策。
2. **CRM 保持原样**：`/customer-management` 与 `?tab=` 机制不动（外部依赖：企微回调、手册、可能的应用菜单）。仿真稿里 `/crm/pool` 式的路径式 Tab 不可照搬；"更多"折叠可以在页内 Tab 栏里实现。
3. **用户 360 保持 `/user-workbench?userId=`**：用户列表点击进入的机制现在就是这样；它在导航里归属"用户与设计师"，但不是 Tab。需要 `navConfig` 支持"隐藏页面归属某个分组"。
4. **`data-admin-page` 改用稳定的 `styleKey`**（R-1 的解法）。
5. **将来若要改网址**，重定向必须透传查询参数（如 `/user-workbench?userId=1` → 新地址时保留 `userId`），并同步修改后端 `wecom_identity.go:562,614`。**仿真稿的旧网址重定向没有透传 query，这是仿真稿的缺陷。**
6. **AI 配置**：外层是"系统设置"的 Tab，内层保留页面自带的"计费/接口"分栏，视觉上区分两层。
7. **建规资料**：D-13 确认后，若需要审核则在"内容运营"下补一个 Tab（后端接口已齐，只缺页面）。

## 7. 发布与回滚

| 项 | 做法 |
|---|---|
| 灰度开关 | 灰度期保留旧侧栏，用本地开关（如 `?nav=old` 或 `localStorage.adminNav`）切换；约 1～2 周后删除旧实现 |
| 发布顺序 | 导航改造是纯前端，可独立发布；若同期做权限/审计，**后端先发布**（向后兼容旧前端），再发前端 |
| 权限种子 | 做 RBAC 时：导出现有管理账号 → 与负责人逐个核对 → 登记 `management_access` → 每个账号实测登录（R-10） |
| 静态资源 | 保留最近 N 个版本的发布目录（沿用现有 `emptyOutDir:false` 策略，避免已打开的标签页请求旧哈希包 404）；HTML 短缓存 |
| 通知使用者 | 发布前发一页"新旧入口对照表"（25 → 9），并提示 ⌘K 搜索 |
| 回滚 | 前端：切回上一发布目录；开关：切回旧导航；数据库：导航改造不涉及；RBAC 迁移只新增字段/表，不删数据 |
