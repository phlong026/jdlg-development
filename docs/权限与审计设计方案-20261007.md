# 管理后台权限与审计设计方案（供评审）

- 日期：2026-10-07
- 状态：**方案待评审，未实施**（鉴权相关代码按工作纪律需人工评审后才动手）
- 背景：后台使用者 10 人以上，目前所有平台管理员对 156 个管理接口（61 个写操作，含调灵石余额、退款、改 AI 密钥）权限完全相同，且业务操作无审计记录

## 1. 现状与风险

| 现状 | 风险 |
|---|---|
| 权限只有 `platform_admin` / `crm_only` 两档（`management_access` 表） | 任何平台管理员都能改 AI 供应商密钥、调任意用户余额、发起退款；误操作与内部风险敞口等同 |
| 业务写操作只有 `log.Println` | 出了问题（如余额被改）无法回答"谁在什么时候改的、改前是什么值" |
| 前端菜单不按角色收缩 | 客服看到风控台、财务看到 AI 配置，认知负担与误点风险 |

## 2. 设计原则

1. **先审计、后权限**：审计是纯增量（新表 + 新中间件），对现有功能零破坏，可以先上；权限收缩会改变所有人的使用方式，必须评审后再上。
2. **复用现有体系**：角色挂在 `management_access` 表上扩展（加 `roles` 列），不引入新的账号体系。
3. **默认拒绝是终态，不是起点**：灰度期间先"只记录不拦截"，观察 2 周真实访问日志，确认角色划分无误后再开启拦截。

## 3. 阶段 A：操作审计（建议先做，约 2~3 天）

### 表结构

```sql
CREATE TABLE management_operation_audit (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  user_id BIGINT UNSIGNED NOT NULL,          -- 操作人（management 账号）
  username VARCHAR(64) NOT NULL,
  method VARCHAR(8) NOT NULL,                -- POST / PUT / DELETE（只记写操作）
  path VARCHAR(255) NOT NULL,                -- /api/v1/management/users/3
  target_type VARCHAR(64) NOT NULL DEFAULT '',-- users / orders / stones / ai_config ...
  target_id VARCHAR(64) NOT NULL DEFAULT '', -- 路径里的资源 ID
  before_value JSON NULL,                    -- 改前值（余额、精选状态等，敏感字段脱敏）
  after_value JSON NULL,                     -- 改后值
  request_id VARCHAR(64) NOT NULL DEFAULT '',-- 便于关联日志
  ip VARCHAR(45) NOT NULL DEFAULT '',
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_user (user_id, created_at),
  INDEX idx_target (target_type, target_id),
  INDEX idx_created (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 落地方式

- 在 `ManagementAccessRequired` 之后挂一个 `AuditWriteOps` 中间件：非 GET 请求进入前快照关键读值（由各 handler 提供 hook），响应 2xx 后异步写入审计表（带缓冲 channel，满了丢弃并告警，不阻塞业务）。
- 高危接口（灵石调整、退款、AI 密钥、改密码）在 handler 里显式补 `before/after`。
- **"日志管理"页改造为"操作审计"页**：读 `management_operation_audit`，让现在的空壳页（`logs` 表无人写入）变成真正有用的页面——这是顺带解决空壳问题的最短路径。

## 4. 阶段 B：轻量 RBAC（审计观察 2 周后再上，约 1 周）

### 角色定义（按现有业务岗位）

| 角色 code | 名称 | 可访问分组（对应新导航一级入口） | 说明 |
|---|---|---|---|
| `super_admin` | 超级管理员 | 全部 | 现有 platform_admin 平移 |
| `ops` | 运营 | 工作台、用户账号、内容运营、销售线索 | 日常内容和用户维护 |
| `finance` | 财务 | 工作台、订单与支付 | 对账、退款、充值配置 |
| `support` | 客服 | 工作台、异常工单、销售线索（只读跟进） | 售后与线索跟进 |
| `crm_only` | 仅客户管理 | 客户管理 | 现状保留 |

### 实现要点

- `management_access` 加 `roles JSON` 列（一个账号可多角色）；`super_admin` 走旧 `scope=platform_admin` 平移，避免迁移风险。
- 后端：`ManagementAccessRequired` 读出角色集合，路由注册处声明所需角色（`managementAuth.RequireRole("finance")`），无角色 → 403。
- 前端：`navConfig.ts` 每个分组标 `roles`，`/me` 返回角色后侧栏自动收缩；无权页面直接不渲染入口（后端仍强校验，前端只是视觉收敛）。
- 灵石调整、退款、AI 密钥三类操作额外要求 `super_admin` 或显式授权。

### 验收方式

- 角色 × 接口矩阵测试（5 角色 × 156 接口的自动化断言）
- 审计表抽查：每角色做一轮真实操作，确认记录完整
- 回退开关：`MANAGEMENT_RBAC=off` 环境变量可整体关闭拦截回到现状
