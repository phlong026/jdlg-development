# 分享网页到小程序的可信交接

日期：2026-10-27。此增量复用现有 Share、Entry、Accept 和通知队列，不新增依赖或数据库表。实现与测试不代表真实 URL Link、微信卡片或服务号外发已经验收。

## 业务语义

H5 与小程序分别保留自己的访问事实。交接只证明“这次小程序入口由这次已接受的 H5 页面浏览发起”，不把匿名网页访客认定为某个账号，不写 `identity`，也不按 IP、设备或时间窗口猜测身份。Share 及其实际分享人始终保持原值。

只有用户在网页同意采集且 H5 `page_view` 已被服务端接受，网页才可携带交接证明。页面 GET、封面预取、点击打开小程序、调用 URL Link 接口本身均不会生成阅读事实。

有效交接的目标**首个页面浏览**不重复提醒；相同页面的事件重试保持去重。目标之后不同 `page_view_id` 的独立阅读按原规则提醒，不因同一个 Entry 最长可用 72 小时而长期压制提醒。首次页面浏览也必须发生在交接凭据的五分钟有效期内，超时按普通 `st` 浏览处理。

## 接口

`POST /api/v1/share-web/open-miniprogram` 保留现有同源、请求头、请求体和速率限制。请求：

```json
{
  "code": "原分享凭据",
  "source_entry_token": "网页Entry凭据",
  "source_page_view_event_id": "已接受的网页浏览事件ID",
  "handoff_token": "网页WebCrypto生成且本次尝试稳定的随机值"
}
```

后三项可省略；它们是交接证明，不能代替 Share。`handoff_token` 要求 32–128 个允许的 URL-safe 字符。服务端检查：

- Share 存在、未撤回、未过期，公开文章及精确发布版本仍有效。
- 来源 Entry 由 H5 服务端入口创建、仍有效、匿名，记录的告知版本等于当前告知版本。
- 来源页面浏览已持久化为 accepted 事件，服务端 `received_at` 在最近五分钟；Entry、事件和 Share 的 owner、route、content、version、session、share 均一致。
- 来源访客和会话没有删除墓碑。

验证通过，先持久化交接证明，再把 `ht` 加入**小程序目标 query**，与原 `st` 一起传入微信生成 URL Link。不能把 `ht` 拼在微信返回网址外层。响应增加 `handoff_ready` 与仅在成功时返回的 `handoff_expires_at`，有效期五分钟且不超过 Share 到期时间。

URL Link 缓存以 Share 与交接 token 分开；不同 token 不会拿到其他访问者的交接网址。同 token 并发仍复用生成结果，速率限制仍按 Share 计算。URL Link 本身可以比交接证明更长寿命，五分钟后只剩普通 `st` 的打开与归因能力。

缺少、过期或不匹配的证明仍可取得只有 `st` 的普通 URL Link，响应 `handoff_ready=false`。数据库或解析故障明确返回错误，不把不可用的仓储当成无证明后继续生成。URL Link 配置未就绪时在创建交接或调用微信前拒绝。

小程序既有 `POST /api/v1/miniprogram/tracking/entry` 增加可选 `handoff_token`。在现有租户写事务中兑换：同 Share 和五分钟内才有效；首次兑换锁定服务端推导的访客及客户端；相同访客和客户端重试可关联，不同账号或客户端重放只按普通 `st` 进入，不获得交接关联或新权限。

## 存储与提醒

复用 `tracking_records`：

| kind | 所属侧与内容 |
| --- | --- |
| `share_handoff` | 以 token 散列为 ID；H5 源访客/会话、Share、内容版本、源事件、到期时间，以及不含目标身份的 `redeemed` 标志 |
| `handoff_redeem` | 以同一散列为 ID；目标访客/客户端、本端会话和首个目标页面标识，不含源访客或源会话 |
| `handoff_notice` | 以源事件散列为 ID；归 H5 源访客/会话，正文仅 `{ "claimed": true }`，没有目标访客、客户端、会话或事件 |

Entry 内部的交接键、H5 来源标记和告知版本只写持久化包装，不出现在 Entry API 响应中。旧 Entry 缺少来源证据，不能生成交接证明。

Accept 仍先接受目标事件。每个已接受的 `page_view` 都会登记有效交接的首个目标页面，即使当时浏览提醒已关闭；非页面浏览事件不读取交接记录。通知关闭期间只登记首个目标页面，不占用源 `handoff_notice`，恢复通知后不同页面的独立阅读按普通规则提醒。只有原本符合浏览提醒规则的事件才参与源级提醒去重：有效首个目标页面若已有源 `notice_event`，不再生成目标提醒；源端未提醒时，原子占用源 `handoff_notice` 后由该目标生成一次提醒。首个页面登记、该 claim、目标事件、通知事件和队列仍处于同一事务，投影失败会整体回滚。提醒对象始终来自原 Share 的真实分享人。

## 隐私与保留期

- 删除 H5 源访客会清理源事实、源通知及 `share_handoff`、源 `handoff_notice`；小程序独立事实不跨端删除。
- 删除目标访客会清理本端事实、目标提醒及 `handoff_redeem`；H5 匿名事实保留。
- **源级无身份 claim 是明确例外**：目标删除时保留不含目标身份的 `handoff_notice`，避免同一个源事件预先生成的另一个 token 再次补发提醒。它随源访客删除或原始保留期清理。
- 源 `share_handoff.redeemed=true` 同样不含目标身份，目标删除不会重置该位，因此已使用 token 不会重新被另一账号兑换。
- 删除源证明后，目标兑换行至多剩不可解析的随机散列，不含源身份；目标自己的事实仍归其本人，后续不再从缺失的源证明建立交接。
- 三个 kind 纳入原始保留期维护。没有自动启动破坏性清理任务。

## 验证边界

领域回归覆盖有效兑换、同客户端重试、跨账号/客户端/Share、过期、未接受或非网页来源、告知版本改变、源撤回、仓储故障、原子失败回滚，以及只对首个及时目标浏览去重。HTTP 回归使用本地微信假服务验证两个 `ht` 的 URL Link query 和缓存隔离，不发真实微信请求。

atomic 与 staged 隐私回归覆盖两端删除互不误删、token 消费位不复活，以及“同源两个 token → C 收到提醒 → 删除 C → D 打开第二 token”保留 D 事实而不再补发提醒。

客户端已整合：H5 只采用准确 event_id 的 accepted/duplicate 响应，最多等一秒确认；同次尝试保留随机交接 token，关闭记录后不再携带证明。小程序的 ht 与 st 同生命周期消费，失败重试保留，成功、隐藏、账号变化或撤回同意后清理。创建新分享会移除旧 ht。H5 与 Mini 定向30项测试通过，类型及生成物检查通过。

真实隔离 MySQL 已验证原生引用持久化、H5 与小程序两条独立 event、一条 notice_event 及实际分享人一条消息中心记录；没有写 identity。命令返回 `PASS / ok service/route 3.160s`，测试容器完成后停止。素材为合成数据，没有调用微信 URL Link、服务号或生产数据库。完整微信跳转和真机跨端仍待验收。
