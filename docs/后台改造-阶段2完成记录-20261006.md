## 2. 实现方式（为什么风险低）

- **页面网址一律不变**，24 个样式文件零改动；Tab 直接指向原有网址。
- **子导航条放在顶栏与内容区之间**（原书签栏的位置），内容区本身不变。
- 导航数据只在 `navConfig.ts` 一处维护；旧导航数据保留，供回退使用。
- 路由一致性脚本新增"**导航覆盖**"检查：每个路由都必须归属某个分组，否则页面会从导航里消失。已反向验证：临时去掉 `/oss` 的归属，脚本立即报错。

## 8. 「用户账号」与「销售线索」的区分（2026-10-06）

**问题**：验收时指出两点：① 客服线索工作台这一组只有一个页面，没有分类；② 「用户与设计师」和「客服线索工作台」名字相近，容易被误解。

**业务上的区别**（依据 `customer_leads` 表：姓名 / 电话 / 微信 / 需求摘要 / 房屋层数 / 风格 / 地块尺寸 / `user_id`）：

| | 用户账号 | 销售线索 |
|---|---|---|
| 是谁 | 已注册小程序账号的人（用户、设计师） | 在智能客服里留了联系方式、有建房需求、待销售跟进的人 |
| 谁处理 | 运营、审核 | 客服、销售 |
| 做什么 | 账号、认证、会员、灵石 | 判断意向、分配负责人、定时跟进 |

线索表里的 `user_id` 可以关联到用户账号，但两者不是一回事；启用 CRM 后，客户管理是「线索 → 客户」的下一步。

**改动**：

| 项 | 做法 |
|---|---|
| 名字与定义 | 「用户与设计师」→「**用户账号**」（说明：已注册的小程序用户）；「客服线索工作台」→「**销售线索**」（说明：留了联系方式，待跟进）；侧栏分组名下带一行灰色小字，悬停有提示；顶栏标题同步 |
| 补分类 | 线索页原有的 6 个队列升级为子导航 Tab：待处理 / 今日新增 / 高意向 / 超时未跟进 / 未分配 / 全部线索；待办类队列带数量角标；队列由地址 `?queue=` 决定（可收藏、可分享），**页面路径不变**；页内不再重复显示队列卡片 |
| 互相跳转 | 用户 360 → 「查看关联线索」（只看该用户，顶部有过滤提示条，可清除）；线索行 / 详情 →「查看用户账号」；匿名线索显示「未关联用户账号」 |
| 去掉重复入口 | 启用 CRM 时，「客户管理」不再在侧栏单列，改为挂在「销售线索」右侧入口（线索 → 客户），二级页有「返回销售线索」 |
| 后端 | `GET /customer-leads` 新增可选参数 `user_id`；不传或非法值视为不过滤，原有调用不受影响 |
| 本地种子 | `dev.sh seed` 增加 5 条虚构线索（含同一用户 2 条、匿名 1 条），可重复执行 |

**顺带修的一个缺陷**：`SubNav` 在二级页只有 1 个页面时整条不渲染，「返回」链接随之消失；以前二级页都有 ≥2 个 Tab 所以没暴露，是这次把"启用 CRM 的导航"补进自动化测试时发现的。

**验证**：`tsc` 零报错；路由一致性通过；回归 **71/71**（新增 5 项：侧栏说明、队列 Tab 与角标、线索 ⇄ 用户互跳与清除过滤、启用 CRM 时的导航、`user_id` 过滤的 API 契约）；后端新增 1 个单测（红 → 绿）；手机宽度下页面无横向溢出，队列 Tab 可左右滑动；内容区像素比对只有线索页与客户管理页有差异，且客户管理页的差异仅为种子数据让数字从 0 变 4。

**「启用 CRM」的导航首次得到测试**：用浏览器拦截 `/me` 把 `crmEnabled` 改为 `true` 来模拟（本地没有真实 CRM 接入，页面里的 CRM 数据请求会 503，与导航无关）。

**未做 / 待你决定**：

- 「异常工单」仍是单页分组（与线索原来的问题相同）；它是客服的售后处理，和销售线索不同对象，建议先不动；
- 用户管理页的「用户管理」标题与侧栏「用户账号」不完全一致，没有改（路由标题影响面较大，若要统一再改）；
- 旧导航（`?nav=old`）保持原样，仍显示旧名字，便于回退对照。

## 9. 销售线索概览区（参考企业微信「销售」页）（2026-10-06）

**需求**：销售线索页参考企业微信的「销售」页：入口卡片（客户 / 线索 / 商机）→ 团队简报 → 线索阶段环形图。

**做法**（仅单独打开 `/customer-leads` 时；嵌在客户管理里的线索栏目保持原样）：

| 区块 | 内容 | 数据来源 |
|---|---|---|
| 入口卡片 | 橙色「线索」；启用 CRM 且为平台管理员时多一张蓝色「客户」（→ 客户管理） | 会话里的 `crmEnabled` |
| 线索简报 | 新增线索 / 待处理 / 高意向 / 超时未跟进（超时为红色），带「刷新」 | `GET /customer-leads/overview` |
| 线索阶段 | 环形图 + 图例：新线索 / 跟进中 / 已成交 / 无效，显示数量与占比，右上「全部 ›」进入全部线索 | 同上，四个阶段之和 = 总数 |

**没有照搬的部分**：参考图里的「商机」、「待再次沟通 / 有意向 / 已加微信 / 转商机」等阶段，本系统的线索表（`customer_leads.status`）里没有这些取值，不虚构数据，阶段用实际存在的四个状态；「团队 / 个人简报」切换、「今天」下拉也没有做（线索表没有按人 / 按时段汇总的接口）。若以后要有「商机」阶段，需要先在业务和数据上定义。

**顺带发现并修复的数据口径问题**（原有缺陷，我上一版把它带进了 Tab 角标）：

| 现象 | 原因 | 修复 |
|---|---|---|
| 「未分配」的数量 = 状态为「新线索」的条数，与点进去的列表条数对不上 | 总览用 `new_count`，而队列条件是「待跟进且无负责人」 | 总览新增 `unassigned_count`，与队列列表共用同一段 SQL 条件 |
| 「高意向」数量包含已成交的高意向线索，与队列列表对不上 | 总览按意向等级统计，队列还要求状态为待跟进 | 新增 `high_todo_count`，Tab 角标与简报都用它 |
| 总览没有「无效」数量 | — | 新增 `invalid_count`，四个阶段之和等于总数 |

「队列条件」抽成两个常量，列表（`ListLeads`）与总览（`Overview`）共用，单测检查各自恰好在这两处被使用，防止以后再漂移。

**踩到的坑**：`responsive.scss` 里有按类名后缀匹配的通配规则（`[class$="-stats"]` 等），在手机宽度下会把网格强制改成单列。新区块的数字网格因此一度在手机上竖排，已换类名并在样式里留了注释。

**验证**：`tsc`、路由一致性、生产构建通过；回归 **74/74**（新增：总览数量与列表条数一致、阶段之和等于总数、概览区数字自洽、启用 CRM 时出现「客户」入口）；`go vet` / `go test` 通过（新增单测先红后绿）；桌面、启用 CRM、手机三种宽度均无横向溢出；像素比对只有线索页与客户管理页变化（后者仅因种子数据变化）。

本地种子线索扩充到覆盖各种状态 / 负责人组合（新线索、跟进中、已成交、无效；有 / 无负责人），使各队列数量互不相同，数量一致性检查才有区分度；需要重新执行 `dev.sh seed`。

- **导航**：三张彩色入口卡片「客户 · 线索 · 商机」放在**布局层**（顶栏下方），客户页、线索页、商机页都显示，当前所在那张高亮，所以任何一页都能切到另外两类；不再使用顶部文字 Tab。侧栏点「销售线索」仍进入「线索」。
- **客户**：对平台管理员**始终显示**；启用 CRM 时为蓝色可用，未接入时灰色并标注「未接入」（点进去仍是客户管理页，其「线索 / 账号与权限」栏目不依赖 CRM）。起初只在启用 CRM 时才出现，使用者反馈「没有看到客户卡片」后改为始终可见。
- **线索**：橙色卡片，带待处理数量角标。
- **商机**：灰色「未启用」；按决定先搭结构，`/opportunities` 是占位页，只说明未启用，不展示任何数字、不造数据。
- **线索页内容**（自上而下）：线索简报 + 线索阶段（桌面端**并排**，首屏就能看到列表开头）→ 队列筛选条（待处理 / 今日新增 / 高意向 / 超时未跟进 / 未分配 / 全部线索，每个都带数量，待办类用橙红色）→ 搜索与列表。
- **去掉「智能客服漏斗」**：它按「客服会话」统计事件（进入客服 → 完成需求采集 → 点击生成 / 转人工 → 提交线索），回答的是「AI 客服转化得怎么样」，面向运营 AI 客服的人；线索阶段按「线索」统计状态，回答「手上的线索跟进到哪了」，面向销售。两者不冲突，但用户不同，且漏斗有三处问题：最后一步「已成交」与线索阶段重复；前 5 步按会话数、最后一步按线索数，单位混用；「点击生成」与「转人工」是并列路径而非先后。页面不再显示、也不再请求漏斗接口，前端对应代码（接口函数、类型、样式）一并删除；**后端接口与事件表保留**（线索详情的时间线要用事件）。以后若要看客服转化，建议放到「AI 运营」里做成真正的漏斗图，只保留进入线索之前的几步。
- **本地种子**：线索种子改为每次先清掉上次的 `LOCAL-S*` 再重建（原先重复执行会因线索合并而失败），并补一条仍待跟进的高意向线索。
